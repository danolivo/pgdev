## 1. Что сделано

Три независимых артефакта, выросших из одного разговора.

### 1.1. Патч: ускорение support-функций numeric

Коммит `4df353c`, файл `src/backend/utils/adt/numeric.c`, +187/−34.

Суть — две правки:

1. **Распаковка packed-значения в буфер на стеке вместо `DatumGetNumeric`.**
   Значение numeric лежит в кортеже с однобайтовым varlena-заголовком, а все
   макросы `NUMERIC_*` рассчитаны на четырёхбайтовый, поэтому
   `PG_GETARG_NUMERIC` делал `palloc` + `memcpy` на каждый вызов. Добавлен
   помощник `numeric_unpack_local()` и тип `NumericLocalBuf` (буфер на 32
   digits ≈ 128 десятичных цифр). Откат на `DatumGetNumeric` — только для
   сжатых, вынесенных в TOAST и слишком длинных значений.
   Применено к: `hash_numeric`, `hash_numeric_extended`,
   `numeric_cmp/eq/ne/lt/le/gt/ge`, `numeric_fast_cmp`.
2. **memcmp-быстрый путь в `numeric_eq`.** Совпадение байтов гарантирует
   равенство значений; значения одной колонки делят dscale, поэтому попадание
   почти стопроцентное. Корректно только для равенства, не для порядка.

**Проверено:** core-регрессия 245/245 зелёная; значения
`hash_numeric`/`hash_numeric_extended` побайтово совпали со стоковой сборкой
на корпусе из нулей разного масштаба, NaN, ±Inf, 400-значных чисел и суммы по
миллиону строк. Бит-точность хэша принципиальна: он участвует в раскладке
hash-партиционированных таблиц и лежит на диске в GIN `jsonb_path_ops`.

### 1.2. Спека: `specs/task_numeric_fixed_width.md`

Коммит `e18878f`. Исходная постановка задачи «numeric как тип фиксированной
длины для 1С-дистрибутива» плюс всё, что выяснилось в разговоре: §3.5 хэш,
§3.6 амплификация WAL и бэкапа, §3.7 границы парка, §3.8 расширения,
§5.6–5.7 новые решения к фиксации, §7 базовая линия замеров, переписанные §6
и §9.

### 1.3. Статья: `articles/why-numeric-is-slow.md`

Коммиты `9e16537`, `52ab608`, `62a33d2`, `bcdd2d8`, `3366be5`. Черновик для
Хабра, ~60к знаков. Структура: хронология работ в hackers → семь причин
медлительности → патч с замерами → чего починить нельзя → обзор соседних СУБД
→ decimal128 → практические советы. Схемы псевдографикой в блоках кода.

## 2. Замеры и как их воспроизвести

PostgreSQL 20devel, `-O2 -g -fno-omit-frame-pointer`, 4 vCPU, `shared_buffers
= 2GB`, `work_mem = 2GB`, `jit = off`, параллелизм выключен. Миллион строк,
двадцать колонок, минимум из пяти прогонов.

| сценарий | int | numeric до | numeric после |
|---|---|---|---|
| seqscan + deform 20 колонок | 72 мс | 119 мс | 119 мс |
| `sum(hash_*(c1))`, 1 колонка | 62 мс | 110 мс | 98 мс |
| `GROUP BY` 20 колонок → 1M групп | 1031 мс | 1572 мс | без изменений |
| `GROUP BY` 20 колонок → 1k групп | 459 мс | 1425 мс | **826 мс** |

Отставание от int в горячем случае: 3.10× → 1.79×.

Ключевое наблюдение: разрыв утраивается только когда группы повторяются, то
есть когда включается сравнение ключей. Основная статья расхода — не
арифметика и не хэш, а `palloc` в `numeric_eq`, вызываемом 20 раз на зонд по
два аргумента.

**Воспроизведение с нуля** (окружение было root-only, поэтому кластер
поднимался под отдельным пользователем):

```bash
apt-get install -y flex bison            # в чистом образе не было flex
./configure --prefix=$HOME/pgi --without-icu --without-readline \
            --without-zlib --enable-debug CFLAGS="-O2 -g -fno-omit-frame-pointer"
make -j4 -s install
# initdb нельзя под root:
useradd -m user && chown -R user $HOME/pgdata $HOME/pgi
su user -c "initdb -D ~/pgdata -U postgres --no-sync && pg_ctl -D ~/pgdata -w start"
```

Схема данных: таблица `ti` с 20 колонками `int4` со случайными значениями до
1e6; `tn` — те же значения через `::numeric(15,2)`; `ti2`/`tn2` — то же, но
1000 различных строк, повторённых по 1000 раз (низкая кардинальность).
Запросы — `SELECT count(*) FROM (SELECT c1..c20 FROM t GROUP BY 1..20) s`,
`SELECT count(c20) FROM t` для изоляции deform и
`SELECT sum(hash_numeric(c1)) FROM t` для изоляции хэш-функции.

Полезная мелочь: `pg_column_size` на литерале даёт 10 байт, а на том же
значении в таблице — 7. Это и есть разница packed/unpacked заголовка,
хороший способ показать проблему в одну строку.

## 3. Что нужно доделать — и почему именно с доступом в интернет

В этой сессии egress-политика окружения резала почти всё: разрешён был только
GitHub и пакетные реестры. `curl` получал `403 Forbidden` на CONNECT,
Chromium (он в образе есть, `/opt/pw-browsers/chromium-1194/chrome-linux/chrome`)
— `ERR_TUNNEL_CONNECTION_FAILED`. Заблокированы в том числе `postgresql.org`,
`duckdb.org`, `clickhouse.com`, `learn.microsoft.com`, `pgxn.org`,
`altinity.com`, `oracle-base.com`, `en.wikipedia.org`.

Поэтому всё, что ниже, собрано из выдержек поисковой выдачи, а не с самих
страниц. **Это главная задача для следующей сессии — открыть и сверить.**

### 3.1. Проверено дословно, сверять не обязательно

- **DuckDB**, [numeric types](https://duckdb.org/docs/current/sql/data_types/numeric):
  «Decimal values with a width above 19 are slow, as arithmetic involving the
  INT128 type is much more expensive than operations involving the INT32 or
  INT64 types. It is therefore recommended to stick with a WIDTH of 18 or
  below.» — цитата подтверждена точным поиском по домену.
- **SQL Server**, [MS-TDS](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-tds/5e02042c-a741-4b5a-b91d-af5e236c5252):
  целое 4/8/12/16 байт по точности плюс байт знака → 5/9/13/17 байт.

### 3.2. Требует сверки — на этом в статье строятся утверждения

1. **ClickHouse** — [документация по Decimal](https://clickhouse.com/docs/reference/data-types/decimal):
   формулировка про эмуляцию 128 и 256 бит. Пересказана близко к тексту, но
   глазами не читана. Риск низкий (дословно совпадает с DuckDB), но проверить
   стоит — на этой паре цитат держится вывод про int128.
2. **Ускорение умножения numeric «от 25 до 81 %»** — число из выдержки по
   [ветке Joel Jacobson / Dean Rasheed](https://www.postgresql.org/message-id/CAEZATCV2qPTGo2Fd8xDs06Q7iU5aorgSa9+Fw9zkuQv1y15rcw@mail.gmail.com).
   Найти, к какому именно патчу оно относится, и не смешаны ли там несколько
   вариантов.
3. **Ветка [«Improving and extending int128.h to more of numeric.c»](https://www.postgresql.org/message-id/CAEZATCWjPZ6w_JZDZmDJPJhYKKJZx8ywxbZYbvSbtrtKyvN-qw%40mail.gmail.com)**
   — закоммичена ли. В выдержке было «Dean Rasheed indicating plans to push it
   shortly in August 2025»; в статье формулировка обтекаемая («расширяют»),
   уточнить и поправить.
4. **Коммит 2012 года** [«Speed up operations on numeric, mostly by avoiding

5. **Замеры pgdecimal2** ([PGXN](https://pgxn.org/dist/pgdecimal2/)): «decimal64

6. **Db2 / POWER6 DFP** — утверждение про аппаратный блок десятичной плавающей

### 3.3. Чего не искали вовсе — стоит поискать

- Свежие ветки hackers 2025–2026 про numeric, которых нет в хронологии статьи.
- Обсуждали ли когда-нибудь в hackers именно **packed-заголовок в
  support-функциях** — прямые предшественники патча §1.1, чтобы не
  переоткрывать и корректно сослаться в письме.
- Реальные отзывы пользователей (не документация) про медленный numeric:
  StackOverflow, DBA.SE, блоги — для раздела статьи «А как у соседей?» это
  добавило бы живых голосов вместо одних вендорских доков.

## 4. Открытые решения

### По патчу

Он самодостаточен, не меняет ни семантики, ни хэш-значений, поэтому переносим
в сообщество независимо от 1С-задачи. Не сделано:

- письмо в pgsql-hackers с замерами (и ссылкой на коммит 2012 года, см. §3.2.4);
- профилирование под `perf` — в окружении его не было, вклад отдельных статей
  разделён косвенно, через A/B прогоны;
- проверка на платформе со строгим выравниванием: `numeric_unpack_local`
  копирует в выровненный буфер и потому безопасен, но глазами это не
  проверялось нигде, кроме x86-64;
- не рассмотрено распространение того же приёма на `numeric_add/sub/mul` и на
  входы агрегатов — там результат всё равно паллочится, но копию входа можно
  не делать.

### По статье

- Нужна КДПВ 1200×600 без текста на картинке, хабы и теги.
- 60к знаков — много. Естественный шов: первая часть «почему медленно» с
  замерами и патчем, вторая — «как у других и что делать» с обзором СУБД и
  decimal128. Разделить на две статьи или оставить лонгридом — решение не
  принято.
- Схемы сейчас псевдографикой в блоках кода (на Хабре рендерится моноширинным
  гарантированно). Обсуждалась, но не делалась, отрисовка их нормальными SVG.
- Если патч пойдёт в hackers, порядок стоит выбрать сознательно: письмо
  раньше статьи, иначе после ревью придётся править цифры.

### По спеке

- **decimal128 как готовая альтернатива самодельному `FixedNumeric`** — не
  внесено в §5 отдельным решением, хотя обсуждалось. За: 34 цифры покрывают
  контракт на 32, формат стандартный, библиотеки и прошлые попытки есть.
  Против: 34 < 38 цифр, на которые спека закладывается как на потолок
  промежуточных вычислений.
- **Предупреждение про int128** (§3.1 этого документа) не отражено в §5.1
  спеки. Два независимых движка документируют, что 128 бит — медленная
  ступень; при контракте на 32 цифры int128 обязателен, то есть формулировка
  §1 «арифметика в регистрах» завышена и требует правки.
- Замеры §6.1 (объём, WAL, бэкап на реальном 1С-датасете) не делались —
  нужны данные, которых в этой сессии не было.

## 5. Фактические поправки, сделанные по ходу

Чтобы не воспроизводить их заново:

- `NaN = NaN` в PostgreSQL истинно **и для float8 тоже**, не только для
  numeric. Отступление от IEEE 754 сделано для обоих типов ради
  согласованности btree и hash. Первоначальное утверждение «в отличие от
  float» было неверным.
- `numeric(15,2)` на 1С-профиле значений занимает **7 байт**, а не 9–11, как
  было в исходной спеке. Рост при переходе на фиксированные 24 байта ближе к
  ×3, чем к ×2.2.
- Фраза «для денег numeric правильный тип, и никакой float его не заменит»
  неверна как абсолютное утверждение: IEEE 754 decimal128 — контрпример.
  Верна только применительно к двоичному float.
- `ALTER TABLE ... SET STORAGE PLAIN` **не** заставляет PostgreSQL хранить
  numeric с четырёхбайтовым заголовком, если исходный датум уже короткий:
  `heap_fill_tuple` копирует короткий датум как есть, до проверки
  `attispackable`. Попытка сделать «естественный эксперимент» на двух
  таблицах с разным storage не удалась по этой причине — сравнивать пришлось
  A/B-прогонами до и после патча.
