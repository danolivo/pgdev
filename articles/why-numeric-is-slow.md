# Почему тип numeric такой медленный

Есть замер, который я показываю коллегам, когда заходит разговор про деньги в базе. Берём таблицу на миллион строк с двадцатью колонками и группируем по всем двадцати сразу. Один раз — когда колонки объявлены как `int`, второй раз — когда те же самые числа лежат в `numeric(15,2)`.

```
GROUP BY по 20 колонкам, 1 млн строк:

  int      →   459 мс
  numeric  →  1425 мс
```

Разница в три раза. Причём данные одинаковые: в numeric-версию я просто скопировал те же значения с двумя нулями после запятой.

Дальше начинается интересное. Если поменять запрос так, чтобы все группы оказались уникальными, разрыв схлопывается до полутора раз. Значит дело не в «numeric просто тяжёлый тип» — дело в чём-то, что срабатывает именно тогда, когда группы повторяются.

Я полез разбираться и в итоге написал патч, который убрал 42 % этого разрыва, не меняя ни семантики, ни формата хранения. Но гораздо интереснее оказалась вторая половина: та часть отставания, которую убрать нельзя в принципе. Про неё и статья.

<cut />

Всё, что ниже, проверено на сборке PostgreSQL 20devel с `-O2`, на обычной виртуалке (4 vCPU, `shared_buffers = 2GB`, `work_mem = 2GB`, `jit = off`, параллелизм выключен, минимум из пяти прогонов). Абсолютные числа у вас будут другими, соотношения — примерно такими же.

## Откуда вообще взялся numeric

Прежде чем ругать тип, полезно знать, при каких обстоятельствах он родился. Хронология восстанавливается по git и по архивам pgsql-hackers довольно точно.

**До 6.5 никакого точного десятичного типа не было вовсе.** В Postgres95 в `pg_type.h` из вещественных типов только `float4` и `float8` — ни `numeric`, ни `decimal`. В 6.4 слова `NUMERIC` и `DECIMAL` в грамматике уже были, но это была имитация: парсер [подменял их на `integer`](https://github.com/postgres/postgres/blob/REL6_4_2/src/backend/parser/gram.y#L2951-L2963) и [ругался на всё, что туда не влезало](https://github.com/postgres/postgres/blob/REL6_4_2/src/backend/parser/gram.y#L2992-L3026):

```c
/* src/backend/parser/gram.y, REL6_4_2, строки 2951-2962 */
        | DECIMAL opt_decimal
                {
                    $$ = makeNode(TypeName);
                    $$->name = xlateSqlType("integer");
                    $$->typmod = -1;
                }
        | NUMERIC opt_numeric
                {
                    $$ = makeNode(TypeName);
                    $$->name = xlateSqlType("integer");
                    $$->typmod = -1;
                }

/* строки 2992-3003 */
opt_numeric:  '(' Iconst ',' Iconst ')'
                {
                    if ($2 != 9)
                        elog(ERROR,"NUMERIC precision %d must be 9",$2);
                    if ($4 != 0)
                        elog(ERROR,"NUMERIC scale %d must be zero",$4);
                }
```

То есть `NUMERIC(10,5)` был ошибкой, а `NUMERIC(9,0)` — молча целым числом. Сами разработчики называли это в переписке «brain-damaged» — [Томас Локхарт, 18 декабря 1998](https://www.postgresql.org/message-id/3679FF70.FBDCB083%40alumni.caltech.edu), тред «Upgrades for 6.4.1»: «We've got DOUBLE PRECISION, DECIMAL, and NUMERIC (the latter two are brain-damaged though)». В том же треде, тем же вечером, появилось письмо Вика, с которого всё и началось.

**Настоящий тип появился 30 декабря 1998 года**, коммит [`0e9d75c6ac`](https://github.com/postgres/postgres/commit/0e9d75c6ac97cfb370313b0aff803f9f464d0758) Яна Вика (Jan Wieck), 3611 строк в новом `numeric.c`. Вышел он в PostgreSQL 6.5 (июнь 1999). В `pg_type.h` он сразу записан как `-1`, то есть переменной длины, с описанием «arbitrary precision exact numeric data type».

Мотив зафиксирован в письме Вика [от 18 декабря 1998](https://www.postgresql.org/message-id/m0zr4z8-000EBPC%40orion.SAPserv.Hamburg.dsh.de), за двенадцать дней до коммита. Это ответ на пункт TODO-листа «Add full ANSI SQL capabilities»:

> And NUMERIC (NUMBER in Oracle :-) is defined as a datatype that uses exact representation of arbitrary precise numbers. But everyone has different legal value ranges and defaults for it. The ranges for the precision (number of total digits) varies from 38 (Oracle) to over 1000 sometimes.
>
> I'll hack around a little on it to see what's possible for us.

Вот и вся причина переменной длины: цель была не «сделать быстрый десятичный тип», а «выполнить требование стандарта про произвольную точность, и не хуже, чем у соседей». Планка была выбрана щедро — исходно `NUMERIC_MAX_PRECISION` равнялся 4000 (сейчас 1000).

Цену понимали сразу. Томас Локхарт [ответил на следующий день](https://www.postgresql.org/message-id/367B1658.6B3BD9%40alumni.caltech.edu):

> This is probably the worst part, since you would hate to take the hit representing everything as extended precision even if the actual range is int4/float8.

А сам Вик в день коммита [написал](https://www.postgresql.org/message-id/m0zvBJ1-000EBPC%40orion.SAPserv.Hamburg.dsh.de) фразу, которая хорошо описывает его приоритеты: «Postgres shouldn't become a substitute for arbitrary precision calculators».

**Ключевой момент — 2001 год.** Марк Батлер предложил сделать numeric фиксированной длины ради скорости. Ответ Тома Лейна [от 13 апреля 2001](https://www.postgresql.org/message-id/3077.987145046%40sss.pgh.pa.us) — это, по сути, окончательное архитектурное решение, действующее до сих пор:

> If we were willing to restrict numeric values to a much tighter range, perhaps so. I rather like a numeric type that can handle ranges wider than double precision, however.
>
> I don't have any objection in principle to an additional datatype "small numeric", or some such name, with a different representation. I do object to emasculating the type we have.
>
> (I think it'd be far more helpful to reimplement numeric using base-10000 representation --- four decimal digits per int16 --- and then eliminate the distinction between storage format and computation format.)

Замеры Батлера в том же треде — миллион сложений: PL/pgSQL numeric 14,8 с, float8 10,7 с, Oracle PL/SQL number 2,0 с. То есть жалоба была обоснованной, но решение приняли в пользу универсальности типа, а не скорости.

Дальше — чистая история оптимизации представления:

- **7.4 (2003).** Том Лейн переписывает numeric на base-10000, коммит [`d72f6c7503`](https://github.com/postgres/postgres/commit/d72f6c75038d8d37e64a29a04b911f728044d83b): «I see about a factor of ten speedup on the 'numeric' regression test». До этого арифметика шла по одной десятичной цифре на байт, а на диске лежало BCD — по две цифры в байте, то есть каждая операция начиналась с распаковки. Заодно из заголовка выкинули `n_rscale`: 10 байт → 8. Сама идея base-10000, кстати, [не Лейна, а Вика](https://www.postgresql.org/message-id/m10ctKO-000EBPC%40orion.SAPserv.Hamburg.dsh.de), он её предложил ещё в апреле 1999-го.
- **8.3 (2007).** Однобайтовый varlena-заголовок Грега Старка плюс перестановка полей numeric (коммит `f828f878e9`) — специально, чтобы потом можно было ужать заголовок без слома совместимости.
- **9.1 (2011).** Роберт Хаас добавляет двухбайтовый `NumericShort`-заголовок, коммит [`145343534c`](https://github.com/postgres/postgres/commit/145343534c153d1e6c3cff1fa1855787684d9a38). Итог: типичное значение несёт 3 байта служебных данных вместо исходных 10.
- **14 (2021).** Том Лейн добавляет `Infinity`/`-Infinity`, коммит `a57d312a77`. `NaN` был с самого первого коммита 1998 года.

Итого: numeric — это тип, спроектированный под требование стандарта о произвольной точности, а потом двадцать лет ужимаемый по краям. Всё, что дальше в статье, — следствия того решения 1998 года и его подтверждения в 2001-м.

## Америку я не открываю

Медлительность numeric — старая тема в pgsql-hackers, работа идёт больше десяти лет подряд. Хронология с конкретикой, потому что в популярных пересказах эти пункты обычно перепутаны:

- **2012.** Коммит [`5cb0e33597`](https://github.com/postgres/postgres/commit/5cb0e335976befdcedd069c59dd3858fb3e649b3) «Speed up operations on numeric, mostly by avoiding palloc() overhead». Автор патча — Kyotaro Horiguchi, коммитил Heikki Linnakangas, вышло в 9.3. Появился `init_var_from_num()`: `NumericVar` кладётся на стек, а его `digits` указывают прямо внутрь исходного значения, без `palloc` + `memcpy`. Важная деталь, которую обычно упускают: это касается **арифметики, вывода и приведений** — `numeric_add/sub/mul/div`, `numeric_out`, `numeric_int8`. Функций сравнения и хэширования патч не трогает вообще, `cmp_numerics()` никогда и не пользовался `NumericVar`. В [исходном письме Хоригучи](https://www.postgresql.org/message-id/20120914.172508.259995810.horiguchi.kyotaro@lab.ntt.co.jp) есть базовая линия, которая нам ещё пригодится: `sum()` по 10 млн строк — int 1570 мс, numeric 3930 мс, то есть 2,5×; его патч давал 11 %.
- **2013.** Крейг Рингер предлагает [добавить десятичную плавающую точку IEEE 754:2008 вместе с аппаратной поддержкой](https://www.postgresql.org/message-id/flat/51B7B932.3000407%402ndquadrant.com). Тред закрыл Том Лейн в тот же день: «As near as I can tell, there is no such hardware support… On the whole, I think the effort would be a lot more usefully spent on trying to make the existing NUMERIC support go faster». Патча так и не появилось. К этой ветке мы ещё вернёмся в разделе про decimal128.
- **2013, отдельно.** [Ускорение avg(numeric)](https://www.postgresql.org/message-id/51DAF8E4.20402%40agliodbs.com) — тред закончился коммитом `69c8fbac20` (патч Hadi Moshayedi, коммитил Том Лейн, PostgreSQL 9.4): `sum`/`avg`/`stddev`/`variance` переехали на `INTERNAL`-состояние вместо массива numeric. Заявленные в треде «+25 % на sum и +50 % на avg» — это цифры Павла Стехуле, процитированные Джошем Беркусом, а не результат финального коммита.
- **2015.** [«Using 128-bit integers for sum, avg and statistics aggregates»](https://commitfest.postgresql.org/3/26/), коммиты `8122e1437e` и `959277a4f5`, PostgreSQL **9.5**. Автор — Andreas Karlsson, коммитил Andres Freund (их часто путают). Самые говорящие числа во всей хронологии — из [письма Карлссона](https://www.postgresql.org/message-id/544BB5F1.50709@proxel.se), 10 млн строк, меняется только аккумулятор:

  | запрос | накопитель numeric | накопитель int128 |
  |---|---|---|
  | `sum(int8)` | 2521 мс | 1023 мс |
  | `var_samp(int4)` | 3809 мс | 1033 мс |

  Заметьте: колонки тут целочисленные, numeric вылезает как *внутренний* тип агрегата. Это одна из самых частых ситуаций, когда пользователь упирается в numeric, ни разу его не объявив.
- **2024.** Joel Jacobson и Dean Rasheed разогнали [умножение](https://www.postgresql.org/message-id/CAEZATCV2qPTGo2Fd8xDs06Q7iU5aorgSa9+Fw9zkuQv1y15rcw@mail.gmail.com) и [деление](https://www.postgresql.org/message-id/CAEZATCVHR10BPDJSANh0u2+Sg6atO3mD0G+CjKDNRMD-C8hKzQ@mail.gmail.com). Всё это в PostgreSQL 18, в release notes одна строка: «Improve the speed of numeric multiplication and division (Joel Jacobson, Dean Rasheed)», четыре коммита — `ca481d3c9a`, `c4e44224c`, `8dc28d7eb8`, `9428c001f6`.

  Здесь надо быть аккуратным с цифрами, которые кочуют по пересказам. Знаменитое «от 25 до 81 %» — это [реплика Джоэла Джейкобсона от 5 июля 2024](https://www.postgresql.org/message-id/ce08a807-b3ca-4316-8fcf-98be5dec10a2%40app.fastmail.com), дословно «Impressive speed-up, between 25% - 81%», и относится она к **промежуточной версии v7** патча `mul_var_small`, замеренной **микробенчмарком самой функции `numeric_mul()`**, на операндах в 1–4 базовые цифры (то есть до 16 десятичных), на трёх процессорах. Разброс 1,25× (Core i9-14900K, 1×1 цифра) — 1,81× (Apple M3 Max, 3×3). На уровне запроса `SELECT SUM(var1*var2)` тот же автор получил 11–13 %. Финальные же коммиты меряются иначе: `8dc28d7eb8` (арифметика по основанию NBASE²) обещает «between around 3 and 6 times» на длинных числах — и честно предупреждает о замедлении на 32-битных машинах; `9428c001f6` — «up to around 20 times as fast as the old Knuth algorithm when 'exact' is true».
- **2025.** Ветка [«Improving and extending int128.h to more of numeric.c»](https://www.postgresql.org/message-id/CAEZATCWgBMc9ZwKMYqQpaQz2X6gaamYRB+RnMsUNcdMcL2Mj_w@mail.gmail.com) закоммичена — пять коммитов Дина Рашида в августе 2025, ключевой `d699687b32`, всё это в PostgreSQL **19**. Только это не про ускорение арифметики numeric: речь про то, чтобы `SUM(int8)`, `AVG(int8)`, `stddev`/`var` от int2/int4 считались в 128 битах **на всех платформах**, а не только там, где у компилятора есть родной `__int128`. Дин мерил ~1,3–1,5× на 32-битной системе, Джон Нейлор — 3015 → 2206 мс на s390x. В release notes PostgreSQL 19 отдельной строки про это нет; главным мотивом сам автор называл упрощение кода: «Even if this had zero performance benefit… it's worth doing».

Обратите внимание на закономерность. Почти всё перечисленное — про **арифметику**: умножение, деление, агрегаты. А самая дорогая статья в моём замере, как выяснится дальше, лежит совсем не там.

## Из чего сделан numeric

`bigint` устроен предельно скучно: восемь байт, в них само число. Всё.

`numeric` — тип переменной длины. В терминах PostgreSQL это *varlena*: сначала заголовок с длиной, потом данные. Цифры хранятся не в двоичном виде, а группами по четыре десятичных знака — по основанию 10000. Плюс знак, «вес» (где стоит десятичная точка) и `dscale` — масштаб, с которым значение положено печатать.

Вот как выглядит `123456.00` в колонке `numeric(15,2)`:

```
bigint, значение 123456
┌────────────────────────────────────────┐
│              8 байт: 123456            │
└────────────────────────────────────────┘
   значение целиком, читается одной инструкцией


numeric(15,2), значение 123456.00 — 7 байт
┌───────┬───────────────────┬──────────┬──────────┐
│ 1 байт│      2 байта      │ 2 байта  │ 2 байта  │
│ длина │   знак, dscale=2, │  цифра   │  цифра   │
│ +флаг │      weight=1     │    12    │   3456   │
└───────┴───────────────────┴──────────┴──────────┘
    ↑            ↑                 ↑
 заголовок   заголовок       «цифры» по основанию 10000:
  varlena     numeric            12 · 10000 + 3456
```

Обратите внимание на первый байт. У varlena бывает два вида заголовка: полный на четыре байта и укороченный на один. Короткий применяется, когда полезная нагрузка помещается в 126 байт (`VARATT_CAN_MAKE_SHORT` в `src/include/varatt.h`) — а numeric помещается почти всегда. PostgreSQL называет такие значения *packed*, и на диске они действительно занимают меньше:

```sql
create temp table t(x numeric(15,2));
insert into t values (123456.00);

select pg_column_size(x) from t;              -- 7
select pg_column_size(123456.00::numeric);    -- 10
```

Семь байт в таблице против десяти у того же значения в виде литерала — ровно три байта разницы на укороченном заголовке. Экономия приятная. Дальше выяснится, что за неё приходится платить, причём в самом неудачном месте.

## Причина первая: значение не помещается в регистр

Внутри PostgreSQL любое значение путешествует в виде `Datum` — это машинное слово, восемь байт на 64-битной платформе. Если тип помещается в эти восемь байт, его передают *по значению*: `bigint` живёт прямо в `Datum`, то есть фактически в регистре процессора.

Если не помещается — передают указатель. Тип становится *pass-by-reference*, и это видно в системном каталоге:

```sql
select typname, typlen, typbyval from pg_type
where typname in ('int8','numeric');

 typname | typlen | typbyval
---------+--------+----------
 int8    |      8 | t
 numeric |     -1 | f
```

`typlen = -1` означает «переменная длина», `typbyval = f` — «по ссылке».

Отсюда следует вещь, которую легко упустить: **результат каждой арифметической операции над numeric нужно куда-то положить**. Не в регистр — в память, которую надо выделить.

Выделяется она функцией `palloc` — это внутренний аллокатор PostgreSQL. Он заметно быстрее системного `malloc`, потому что не освобождает память по одному кусочку: вся память, выделенная при обработке одной строки, сбрасывается разом, когда строка обработана. Но «быстрее» не значит «бесплатно».

```
bigint:   a + b  →  одна инструкция, результат в регистре

numeric:  a + b  →  выровнять масштабы
                 →  сложить
                 →  проверить пределы
                 →  palloc под результат
                 →  записать результат в память
```

Это не «плохая реализация», это следствие ширины типа. И, забегая вперёд: даже если завтра переписать numeric на фиксированные 16 или 24 байта, в восемь байт он всё равно не влезет и по значению передаваться не начнёт. Ровно эту стену нащупал Томас Манро в 2017 году, рассуждая про DECFLOAT: «DECFLOAT(9) and DECFLOAT(17) could in theory be passed by value. Of course we don't have a way to make those pass-by-value and yet pass DECFLOAT(34) by reference! That is where I got stuck last time».

## Причина вторая: копия на каждый вызов

Теперь про ту самую экономию трёх байт.

Функции сравнения и хэширования устроены так: они получают `Datum`, приводят его к типу `Numeric` и работают со структурой. Приведение делается макросом `PG_GETARG_NUMERIC`, а он разворачивается в `DatumGetNumeric` → `PG_DETOAST_DATUM`.

И вот тут случается неприятное. Все внутренние макросы доступа к полям numeric написаны в расчёте на четырёхбайтовый заголовок. А в кортеже значение лежит с однобайтовым. Поэтому `PG_DETOAST_DATUM` видит «нестандартный» заголовок и честно делает то, что должен: выделяет память и копирует туда значение с правильным заголовком.

```
Datum из кортежа
      │
      ▼
PG_GETARG_NUMERIC
      │
      ├─► заголовок укороченный? ──► почти всегда да
      │
      ▼
detoast_attr()
      │
      ▼
palloc(10) + memcpy(7 байт)      ◄── на КАЖДЫЙ вызов
      │                               функции сравнения
      ▼
cmp_numerics()  ← собственно работа, ради которой всё затевалось
```

Одна аллокация — это единицы наносекунд. Проблема в том, сколько их набегает.

Вернёмся к запросу из начала статьи. `GROUP BY` по двадцати колонкам выполняется через `HashAggregate`. На каждую входную строку узел делает две вещи: считает хэш от ключа и, если в хэш-таблице нашлась подходящая корзина, сравнивает ключи целиком — то есть все двадцать колонок.

```
на каждую строку HashAggregate:

  1. посчитать хэш ключа
       hash_numeric ×20 колонок          →  20 аллокаций

  2. найти корзину в хэш-таблице

  3. сравнить ключ с тем, что лежит в корзине
       numeric_eq ×20 колонок ×2 аргумента →  40 аллокаций
                                              ─────────────
                                              60 аллокаций
                                              на одну строку
```

Шестьдесят аллокаций на строку, шестьдесят миллионов на запрос. У `int` их ноль: `hashint4` и `int4eq` — это буквально пара инструкций, они не трогают память вовсе.

Вот и объяснение, почему разрыв утраивается именно на повторяющихся группах. Пока все группы уникальны, шаг 3 почти не выполняется — сравнивать не с чем, каждая строка создаёт новую корзину. Как только группы начинают повторяться (то есть в любой реальной агрегации по измерениям), включаются те самые сорок аллокаций.

Это не моя теория — это отдельно измеренный и задокументированный эффект. Самое наглядное свидетельство нашлось в багрепорте [«Fix memory leak in memoize for numeric key»](https://www.postgresql.org/message-id/83281eed63c74e4f940317186372abfd@cft.ru) (Алексей Орлов, ЦФТ, октябрь 2023). Цепочка вызовов там названа буквально:

```
MemoizeHash_hash() → FunctionCall1Coll() → hash_numeric() → pg_detoast_datum() → palloc()
```

Nested loop с memoize по numeric-ключу, 600 000 строк, один промах кэша и 599 999 попаданий. `ExecutorState` до исправления — 24 075 240 байт использовано, после — 74 840 байт. Двадцать четыре мегабайта мусора, порождённые исключительно тем, что хэш-функцию numeric вызвали 600 тысяч раз.

## Причина третья: разбор кортежа

Прежде чем что-то сравнивать, значения нужно достать из строки. Эта операция называется *deform*, и для numeric она тоже дороже.

Строка в PostgreSQL — это заголовок, битовая карта NULL-ов и дальше значения колонок подряд, без разделителей. Чтобы добраться до двадцатой колонки, нужно знать её смещение от начала.

Если все колонки фиксированной ширины, смещение считается арифметически и кэшируется в описателе таблицы — один раз на всё время жизни:

```
20 колонок int4 — смещения известны заранее

┌────┬────┬────┬────┬────┬─── … ───┬────┐
│ c1 │ c2 │ c3 │ c4 │ c5 │         │c20 │
└────┴────┴────┴────┴────┴─── … ───┴────┘
  0    4    8   12   16              76

смещение c20 = 19 × 4 — посчитано один раз, дальше просто читаем
```

Если ширина переменная, так нельзя. Правило записано прямо в коде, в `TupleDescFinalize()` (`src/backend/access/common/tupdesc.c`):

```c
/*
 * Don't cache offsets beyond fixed-width attributes.
 */
if (cattr->attlen <= 0 || ...)
    break;
```

`attlen <= 0` — это ровно случай numeric. Кэш смещений обрывается на первой такой колонке, и дальше каждое смещение приходится вычислять заново, читая заголовок каждого предыдущего значения (сам цикл живёт в `slot_deform_heap_tuple()`, `src/backend/executor/execTuples.c`):

```
20 колонок numeric — у каждого значения своя длина

┌──────┬─────┬────────┬──────┬─── … ───┬─────┐
│  c1  │ c2  │   c3   │  c4  │         │ c20 │
└──────┴─────┴────────┴──────┴─── … ───┴─────┘
  0      7     12       21              ???

чтобы узнать смещение c20, надо прочитать
заголовки c1…c19 — на каждой строке заново
```

В моём замере это 47 миллисекунд на миллион строк: простой `select count(c20) from t` без всякой группировки занимает 72 мс на int-таблице и 119 мс на numeric-таблице.

Это, кстати, единственная из семи причин, вокруг которой прямо сейчас идёт активная работа в ядре — но с другой стороны. Дэвид Роули потратил на deform два цикла: коммит `d28dff3f` (PostgreSQL 18) заменил в описателе таблицы 104-байтовый `FormData_pg_attribute` на 16-байтовый `CompactAttribute` и дал «~10 % TPS на OLAP-агрегации по таблице из 16 полей, до ~25 % на AMD Zen4» — чисто за счёт того, что при разборе трогается меньше кэш-линий. Продолжение [«More speedups for tuple deformation»](https://www.postgresql.org/message-id/CAApHDvpoFjaj3+w_jD5uPnGazaw41A71tVJokLDJg2zfcigpMQ@mail.gmail.com) закоммичено в PostgreSQL 19: в среднем 21 %, на отдельных случаях больше 44 %. Показательно, что половина тестовых случаев в этом бенчмарке отличается ровно одним: первая колонка — `INT` или `TEXT`. То есть «сколько стоит ведущая колонка переменной длины» — это официально признанный вопрос.

Но саму причину это не убирает. Переменная длина — прямое следствие того решения 1998 года, что numeric обязан вмещать числа произвольной точности.

## Причина четвёртая: у одного значения много представлений

Здесь мы уходим от механики к семантике, и дальше будет только фундаментальнее.

Вот что PostgreSQL думает про `1.0` и `1.00`:

```sql
select 1.0 = 1.00;                          -- true
select (1.0)::text, (1.00)::text;           -- «1.0», «1.00»
select hash_numeric(1.0) = hash_numeric(1.00);  -- true
```

Числа равны, но печатаются по-разному. Внутри у них разный `dscale` и, соответственно, разные байты. То есть numeric — тип, у которого **одно значение имеет много представлений**, и разные части системы обязаны относиться к этому по-разному:

```
      1.0            1.00          1.000000
       │               │               │
   dscale = 1      dscale = 2      dscale = 6
   цифра: 1        цифра: 1        цифра: 1
       │               │               │
       └───────────────┼───────────────┘
                       │
        =        →  true     ─┐
        ORDER BY →  вместе    ├─ обязаны игнорировать dscale
        hash     →  одинаково ┘

        ::text   →  «1.0» ≠ «1.00»  ─── обязан помнить dscale
```

Зачем вообще `dscale` нужен, объяснено в комментарии Тома Лейна от 2003 года, он до сих пор стоит в `numeric.c`:

> dscale may be more than the number of physically stored fractional digits, implying that we have suppressed storage of significant trailing zeroes. It should never be less than the number of stored digits, since that would imply hiding digits that are present.

У `bigint` такой проблемы нет: одно значение — одна битовая картинка. Отсюда всё сразу дёшево:

- сравнение на равенство — это сравнение байтов;
- хэш — это перемешивание тех же байтов;
- сортировка — сравнение самих значений, без всякой подготовки.

Для numeric ни одно из этих утверждений не верно. Сравнение обязано сначала привести оба числа к общему масштабу. Хэш обязан считаться не от байтов, а от канонической формы: в `hash_numeric` есть отдельный код, который снимает ведущие и хвостовые нулевые цифры, а для любого нуля возвращает константу (`PG_RETURN_UINT32(-1)`) — иначе `0.0` и `0.000` хэшировались бы по-разному и разъезжались бы по разным корзинам хэш-таблицы, будучи равными. Комментарий там же:

> Note that we don't hash on the Numeric's scale, since two numerics can compare equal but have different scales.

Заметьте: это не про производительность конкретной реализации. Это про то, что у операции сравнения принципиально есть ветвление, зависящее от данных.

А ветвление, зависящее от данных, — это то, что процессор и компилятор ненавидят больше всего. Однородный код вроде «сравнить сто чисел подряд» процессор умеет исполнять пачками, по несколько значений за такт (это и есть SIMD), а предсказатель переходов на нём не ошибается ни разу. Как только внутри появляется «если масштабы разные, то сначала выровнять» — пачками уже не получится, и каждая неверно предсказанная ветка стоит десятков тактов. Для `bigint` компилятор разворачивает сравнение в две-три инструкции; для numeric он вынужден оставить полноценную функцию с ветвлениями.

## Причина пятая: масштаб результата зависит от данных

С арифметикой ситуация ещё веселее. Посмотрите:

```sql
select 1.5 + 1.50;    -- 3.00        (2 знака)
select 2.0 * 3.00;    -- 6.000       (3 знака)
select 10.0 / 4;      -- 2.5000000000000000   (16 знаков)
```

У сложения масштаб результата — максимум из масштабов аргументов. У умножения — сумма. Пока логично. А что с делением?

```sql
select 1 / 3::numeric;         -- 0.33333333333333333333    (20 знаков)
select 1000000 / 3::numeric;   -- 333333.333333333333       (12 знаков)
select 0.001 / 3::numeric;     -- 0.00033333333333333333    (20 знаков)
```

Количество знаков после запятой разное, хотя тип аргументов один и тот же. Отвечает за это функция `select_div_scale()`. Она смотрит на первые ненулевые цифры обоих аргументов, прикидывает порядок частного и выбирает масштаб так, чтобы значащих цифр было не меньше `NUMERIC_MIN_SIG_DIGITS`, а это 16. Комментарий в коде:

> The result scale of a division isn't specified in any SQL standard. For PostgreSQL we select a result scale that will give at least NUMERIC_MIN_SIG_DIGITS significant digits, so that numeric gives a result no less accurate than float8; but use a scale not less than either input's display scale.

Проверить арифметику легко: для `1/3` оценка веса частного равна −1, отсюда `rscale = 16 − (−1)·4 = 20`; для `1000000/3` вес равен 1, отсюда `16 − 4 = 12`. Ровно то, что печатается.

Что это означает практически:

- ширина результата выражения `a / b` зависит от **значений**, а не от типов;
- планировщик не может точно оценить размер результата — только по статистике;
- перед тем как поделить, нужно сначала выполнить алгоритм выбора масштаба, потом домножить делимое на нужную степень десятки, потом поделить, потом округлить.

У `bigint` деление — это одна инструкция процессора, и результат всегда `bigint`.

## Причина шестая: десятичная арифметика на двоичном железе

Всё выравнивание масштабов, всё округление, `round()` и `trunc()` с аргументом — это умножение или деление на 10^k, где k заранее неизвестно.

Когда степень десятки известна на этапе компиляции, компилятор превращает деление в умножение со сдвигом и всё быстро. Когда k приходит из данных — нужна таблица степеней и широкое умножение.

Отдельная история — если попытаться хранить коэффициент в 128-битном целом (а именно так выглядят все проекты «быстрого numeric»). На x86-64 инструкции деления 128 на 128 бит просто нет. Есть `divq`, которая делит 128 на 64 и падает с `#DE`, если частное не поместилось в 64 бита.

Здесь стоит быть точным, потому что тезис часто пересказывают слишком сильно. Я собрал `unsigned __int128` под gcc 13.3 с `-O2` и посмотрел, что получается:

```asm
; a * b — инлайнится целиком, три умножения
umul:   imulq %rdx, %rsi
        movq  %rdi, %rax
        imulq %rdi, %rcx
        mulq  %rdx
        addq  %rcx, %rsi
        addq  %rsi, %rdx
        ret

; a / b, делитель переменный — вызов библиотеки
udiv:   subq  $8, %rsp
        call  __udivti3@PLT
        addq  $8, %rsp
        ret
```

Но деление на маленькую константу компилятор всё-таки инлайнит через умножение на обратную величину: `a / 10` разворачивается в цепочку `mulq`, `a / 1024` — в сдвиг. А вот `a / 10^19` снова уходит в `__udivti3`. Так что честная формулировка такая: **умножение 128 бит — это несколько инструкций, деление на переменный делитель — вызов функции**. Для numeric это существенно, потому что делить на константный NBASE = 10000 дёшево, а вот делить одно значение на другое — нет.

И есть приятный сюрприз в обратную сторону. Печать числа при нынешнем хранении почти бесплатна: цифры уже десятичные, их достаточно выписать. Если перейти на двоичный коэффициент, `numeric_out` станет цепочкой делений — то есть **дороже, чем сейчас**. Всякий раз, когда кто-то предлагает «просто хранить numeric как int128», об этом стоит вспомнить.

## Причина седьмая: результату может не хватить места, и это нормально

У `bigint` всё просто: результат операции над двумя bigint — либо bigint, либо ошибка переполнения. Третьего не дано, поэтому и проверка ровно одна — флаг переполнения процессора.

С numeric так не получится:

- умножение двух чисел по 32 значащих цифры даёт до 64 цифр;
- деление вообще может не заканчиваться — `1/3` в десятичной записи бесконечно.

Значит у **каждой** операции должна быть политика округления. А округление ломает привычные алгебраические свойства: сумма остаётся ассоциативной, а вот произведение после округления — уже нет. Отсюда ограничения на переупорядочивание операций в агрегатах и на распараллеливание.

Кстати, про агрегаты. Состояние `sum(numeric)` не может быть значением того же типа — сумма растёт с числом строк. Внутри для этого есть отдельная структура `NumericSumAccum`. Комментарий к ней объясняет устройство лучше любого пересказа:

> It uses 32-bit integers to store the digits, instead of the normal 16-bit integers (with NBASE=10000). This way, we can safely accumulate up to NBASE - 1 values without propagating carry, before risking overflow of any of the digits.
>
> Positive and negative values are accumulated separately, in 'pos_digits' and 'neg_digits'.

То есть переносы разрядов делаются не на каждой строке, а раз в 9999 значений, и положительные с отрицательными копятся в двух отдельных буферах. Не зря `sum(bigint)` возвращает numeric — по той же самой причине.

## Мелочи, которые тоже не бесплатны

Три вещи, каждая по чуть-чуть.

**Специальные значения.** В домене numeric есть `NaN`, `+Infinity` и `-Infinity` (первый — с 1998 года, вторые появились только в PostgreSQL 14). PostgreSQL сознательно отступает от IEEE 754 и считает, что `NaN = NaN` — это `true`, а сам NaN больше всего остального: иначе btree-индексы и хэш-таблицы работали бы некорректно. То же самое сделано и для float, так что уникальным для numeric это не назвать — но за это платит каждая операция сравнения, каждая арифметическая функция и каждый хэш: у всех в начале ветвление на специальные значения.

**typmod.** `numeric(15,2)` — это не аннотация, а контракт, который проверяется в рантайме. На каждой записи и каждом приведении типа вызывается функция, которая округляет значение до нужного масштаба и проверяет, не превышена ли точность. У `int4` понятия typmod нет вовсе: ширина — свойство самого типа, проверять нечего.

**Сокращённые ключи сортировки.** Для ускорения `ORDER BY` PostgreSQL умеет строить из numeric восьмибайтовый «сокращённый ключ» и сортировать в основном по нему. Но отображение получается неточным, поэтому рядом живёт механизм отката: `numeric_abbrev_abort` оценивает кардинальность по HyperLogLog и, если различных значений набирается меньше одного на 10 000 входов, откатывает всю затею. У `bigint` сортировка идёт по самому значению, и ничего из этого не нужно.

## Что из этого чинится

Вернёмся к аллокациям. Шестьдесят штук на строку — это ведь не свойство типа, это свойство реализации. Функции сравнения и хэширования никогда не отдают значение наружу: они получили два числа, сравнили и забыли. Значит копию можно делать не в куче, а на стеке.

Патч получился небольшим. Вместо `DatumGetNumeric` появился помощник, который:

- если заголовок укороченный — копирует значение в буфер на стеке вызывающей функции;
- если заголовок уже полный — возвращает указатель как есть, без копирования;
- и только для сжатых, вынесенных в TOAST и неправдоподобно длинных значений идёт прежним путём с аллокацией.

Плюс отдельный трюк для `numeric_eq`. Если байты двух значений совпадают, значения точно равны — можно ответить сразу, не разбирая структуру. Обратное неверно (`1.0` и `1.00` равны при разных байтах), поэтому это именно быстрый путь, а не замена сравнению. Зато срабатывает он почти всегда: значения одной колонки имеют одинаковый `dscale` и хранят одни и те же цифры. Важная оговорка: для сравнения на равенство приём корректен, для упорядочивания — нет.

Результат:

| сценарий | было | стало |
|---|---|---|
| `GROUP BY` 20 numeric-колонок, 1000 групп | 1425 мс | **826 мс** (−42 %) |
| `sum(hash_numeric(c1))`, 1 млн строк | 110 мс | 98 мс (−11 %) |
| `GROUP BY` 20 numeric-колонок, 1 млн групп | 1572 мс | без изменений |
| `GROUP BY` 20 int-колонок (контроль) | 459 мс | без изменений |

Отставание от int в горячем сценарии: было в 3,1 раза, стало в 1,8 раза.

Значения хэшей при этом побайтово совпадают со стоковой сборкой — это принципиально, потому что хэш numeric участвует в раскладке hash-партиционированных таблиц и лежит на диске в GIN-индексах `jsonb_path_ops` (`JsonbHashScalarValue()` в `jsonb_util.c` дёргает именно `hash_numeric`). Изменить его — значит сломать существующие базы. Полный набор регрессионных тестов ядра проходит.

### Честная оговорка: идея не новая, и её уже отклоняли

Прежде чем радоваться, я полез в архивы — и правильно сделал. У приёма есть история, о которой стоит знать всякому, кто соберётся его повторить.

- **2015, Грег Старк.** В треде [«LLVM miscompiles numeric.c access to short numeric var headers»](https://www.postgresql.org/message-id/CAM-w4HOwy3EfmR%2BkyT0DLnOnf9u3PhJMOwT-5gVDgM2Gmh8ucA%40mail.gmail.com) он замечает, что предложенное Лейном исправление «would still require palloc/memcpy for data smaller than 128 bytes», и предлагает выделять память только когда цифры не выровнены, то есть только для packed-значений. Это ровно та же мысль. Реализована она не была.
- **2015, Эндрю Гирт.** А вот здесь мысль реализована — и лежит в ядре с PostgreSQL 9.5. Коммит `abd94bcac4` «Use abbreviated keys for faster sorting of numeric datums» в функции `numeric_abbrev_convert()` делает именно это, с комментарием: «This is to handle packed datums without needing a palloc/pfree cycle; we keep and reuse a buffer large enough to handle any short datum». Только в sortsupport, не в сравнении и не в хэше.
- **2011, Том Лейн.** Тот же класс оптимизации для `text`/`bytea` — коммит `1b393f4e5d` «Avoid detoast in texteq/textne/byteaeq/byteane for unequal-length strings», PostgreSQL 9.1.
- **Апрель 2026, Chenhui Mo.** Патч [«Optimize numeric comparisons and aggregations via packed-datum extraction»](https://commitfest.postgresql.org/patch/6651/) — практически то же самое, что описано выше, с формулировкой проблемы слово в слово: «PG_GETARG_NUMERIC() unconditionally detoasts short-header datums, which incurs continuous palloc/memcpy overhead in tight aggregation loops». Заявленные цифры на 20 млн строк, `NUMERIC(18,2)`: `MAX` 980,8 → 297,9 мс (−70 %), все пять агрегатов вместе 1686,7 → 804,5 мс (−52 %). **Статус — Rejected** в коммитфесте PG20-1, закрыт 10 мая 2026 года, причём формальных ревью в треде нет ни одного. В первой версии патча была реальная проблема: на платформах со строгим выравниванием чтение `int16` по нечётному смещению даёт SIGBUS. Во второй версии это исправлено копированием в буфер на стеке. Продолжение — [«Make NumericVar storage semantics explicit»](https://commitfest.postgresql.org/patch/6751/) — отозвано автором 26 июля 2026 года.

Вывод для меня получился двойной. С одной стороны, диагноз подтверждается независимо: и в 2015-м, и в 2023-м (тот самый memoize), и в 2026-м люди приходят к одному и тому же месту. С другой — «патч правильный и приносит 42 %» само по себе не значит, что его примут. Как минимум надо: проверить на платформе со строгим выравниванием, а не только на x86-64; принести замеры на запросах, а не на микробенчмарках; и в письме явно сослаться и на `5cb0e33597`, и на `abd94bcac4`, и на отклонённый апрельский патч.

## Что не чинится никогда

А вот сводка того, во что превращается операция — сейчас и в самой оптимистичной гипотетической реализации с фиксированной шириной и 128-битным коэффициентом.

| операция | bigint | numeric в лучшем возможном виде |
|---|---|---|
| `=` | одна инструкция | ветвление на NaN/Inf, быстрый путь по совпадению байтов, общий путь с выравниванием масштабов |
| хэш | одна инструкция | канонизация значения, затем перемешивание |
| `<` | одна инструкция | ветвление на специальные, сравнение порядков, выравнивание |
| `+` | одна инструкция | выравнивание масштабов, сложение, проверка пределов, аллокация результата |
| `*` | одна инструкция | 256-битный промежуточный результат, масштаб `s1+s2` может превысить предел, округление, аллокация |
| `/` | одна инструкция | выбор масштаба по данным, домножение, деление через libgcc, округление, аллокация |
| `sum()` | регистр | аккумулятор шире самого типа, отдельная логика переносов |
| печать | цикл делений | цепочка делений — **дороже**, чем при нынешнем хранении |

И главный вывод, который меня самого удивил.

Похожими на int операции numeric становятся ровно там, где дело не в арифметике: **равенство, хэш, разбор кортежа, предсказуемая ширина строки**. Именно это я и померил, и именно это можно вычистить.

Арифметика похожей на int не станет никогда. У каждой операции остаются: ветвление на специальные значения, вычисление масштаба результата, политика округления и аллокация под результат. Можно убрать разбор varlena и поразрядный проход — но `numeric + numeric` от этого не превратится в инструкцию `add`.

Интуиция обычно работает наоборот: кажется, что numeric медленный «из-за сложной арифметики», а сравнение и хэш — мелочь. По факту всё ровно наоборот. Самая, на мой взгляд, убедительная иллюстрация — [замер Кааreла Мёппеля из Cybertec](https://www.cybertec-postgresql.com/en/int4-vs-int8-vs-uuid-vs-numeric-performance-on-bigger-joins/) на джойнах: 5 млн строк, 1000 итераций, int4 — 2,72 с, numeric — 3,65 с, то есть +34 %. При этом **индексы одинакового размера, 107 МБ оба**. Никакого проигрыша по объёму, никакого лишнего ввода-вывода — вся разница чисто в процессорном пути сравнения.

## А как у соседей?

Прежде чем говорить, что со всем этим делать, полезно посмотреть, как ту же задачу решили другие. Точный десятичный тип есть везде, и решения заметно различаются.

| Система | Тип | Как хранится | Ширина |
|---|---|---|---|
| PostgreSQL | `numeric` | цифры по основанию 10000, varlena | переменная |
| Oracle | `NUMBER` | мантисса по основанию 100 | переменная, до 21 байта |
| SQL Server | `decimal(p,s)` | целое со сдвигом | 5/9/13/17 байт по `p` |
| MySQL | `DECIMAL(p,s)` | двоичная упаковка по 9 цифр в 4 байта | фиксированная по `p` |
| DuckDB | `DECIMAL(p,s)` | INT16/32/64/128 | 2/4/8/16 байт по `p` |
| ClickHouse | `Decimal32/64/128/256` | знаковое целое | 4/8/16/32 байта |
| Db2 | `DECFLOAT(16\|34)` | IEEE 754 decimal64/decimal128 | 8/16 байт |

Первое, что бросается в глаза: **PostgreSQL и Oracle — единственные в этом списке, у кого точный десятичный тип переменной длины.** Все остальные выбирают ширину и держат её.

И тут важная деталь, которая объясняет, почему PostgreSQL так поступил. В SQL Server, MySQL, DuckDB и ClickHouse ширина хранения выводится из **объявленной точности колонки**. В PostgreSQL так нельзя: `typlen` — свойство типа, а не колонки. Один и тот же `numeric` обязан обслуживать и `numeric(15,2)`, и `numeric` без ограничений вовсе. Раз домен неограничен, длина обязана быть переменной. Мы платим за универсальность — ровно за ту, которую Том Лейн отказался разменивать в 2001-м.

Разница в цифрах получается заметной. `decimal(15,2)` в SQL Server занимает [9 байт](https://learn.microsoft.com/en-us/sql/t-sql/data-types/decimal-and-numeric-transact-sql), в DuckDB — 8 байт (INT64), в PostgreSQL — те самые 7 байт из начала статьи. То есть по объёму мы не проигрываем; проигрываем в том, что нашу семёрку нельзя прочитать одной инструкцией.

**Oracle** — ближайший родственник PostgreSQL: `NUMBER` тоже переменной длины, тоже с мантиссой по составному основанию (у них 100, у нас 10000). [Документация OCI](https://docs.oracle.com/cd/A91202_01/901_doc/appdev.901/a89857/oci03typ.htm) описывает формат так: «The first byte is the exponent and is followed by 1 to 20 mantissa bytes… Because the mantissa digits are stored in base 100, each byte can represent 2 decimal digits». То есть 1 + 20 = 21 байт на значение; [SQL Language Reference](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/Data-Types.html) при этом пишет «Each NUMBER value requires from 1 to 22 bytes», считая ещё байт длины в строке.

И показательно, что именно Oracle в 10g добавил `BINARY_FLOAT` и `BINARY_DOUBLE`. [Database Concepts](https://docs.oracle.com/en/database/oracle/oracle-database/19/cncpt/tables-and-table-clusters.html) формулирует мотив прямо: «whereas NUMBER uses decimal precision, BINARY_FLOAT and BINARY_DOUBLE use binary precision, which enables faster arithmetic calculations and usually reduces storage requirements». То есть вендор фактически признал: `NUMBER` медленный, вот вам быстрая альтернатива — но за точность отвечаете сами.

Насколько медленный, померил Тим Холл — правда, [только на уровне PL/SQL](https://oracle-base.com/articles/misc/performance-of-numeric-data-types-in-plsql), это важная оговорка: 10 млн итераций сложения в локальной переменной дают `NUMBER` 26 сотых секунды против 15 у `BINARY_DOUBLE` и 14 у `BINARY_FLOAT`. Про SQL-уровень и про хранение этот замер не говорит ничего. Забавная деталь оттуда же: `PLS_INTEGER` — 9 сотых, а вот `INTEGER` (подтип NUMBER с проверкой ограничения) — 44, то есть почти вдвое медленнее самого `NUMBER`.

**SQL Server** пошёл другим путём: ширина фиксирована ступеньками по точности. Лучше всего это видно в [спецификации протокола MS-TDS](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-tds/5e02042c-a741-4b5a-b91d-af5e236c5252), где формат описан дословно: «One 1-byte unsigned integer that represents the sign… One 4-, 8-, 12-, or 16-byte signed integer that represents the decimal value multiplied by 10^s». Отсюда знакомая лесенка 5 / 9 / 13 / 17 байт для точности 1–9 / 10–19 / 20–28 / 29–38. То есть внутри `decimal` в SQL Server — обыкновенное целое со сдвигом запятой, ровно «копейки в bigint», только узаконенные и автоматические. Плюс есть тип `money` — [8 байт с фиксированными четырьмя знаками](https://learn.microsoft.com/en-us/sql/t-sql/data-types/money-and-smallmoney-transact-sql) после запятой.

Рэндольф Уэст в [разборе эффективности DECIMAL](https://bornsql.ca/blog/data-efficiency-decimal/) обращает внимание на неочевидное следствие: «A precision of 10–19 digits requires 9 bytes (a 45 % jump in storage required), and this is the sweet spot where a BIGINT is an effective alternative». Если дробная часть не нужна — целочисленный тип выгоднее.

А самый полезный для нас замер по SQL Server — [сравнение расхода CPU на арифметику float против numeric](https://www.mssqltips.com/sqlservertip/5826/comparing-sql-server-cpu-usage-with-arithmetic-for-float-versus-numeric-datatypes/) (Бен Снайдеро, 2018). Полмиллиона строк, `numeric(19,8)` против `float`, замер по `SET STATISTICS TIME`: все четыре операции вместе — **1062 мс CPU против 391 мс**, деление — 547 против 296. Вывод автора: «Every operation against the float datatype uses less CPU than its numeric counterpart, anywhere from 35–45 % less». Порядок величины ровно тот же, что мы видим в PostgreSQL.

**MySQL** интересен направлением движения. До версии 5.0.3 `DECIMAL` хранился **строкой**, по байту на цифру — [официальный мануал 5.0](https://docs.oracle.com/cd/E19078-01/mysql/mysql-refman-5.0/data-types.html) формулирует это так: «Previously, they were stored as strings, with one character used for each digit of the value, the decimal point… and the '-' sign». В 5.0.3 перешли на [двоичную упаковку по девять цифр в четыре байта](https://dev.mysql.com/doc/refman/8.4/en/precision-math-decimal-characteristics.html), с фиксированной длиной, выведенной из точности. Направление то же самое: от гибкого представления к фиксированному.

**Db2** — единственный из мейнстрима, кто пошёл в IEEE-десятичную плавающую точку: [`DECFLOAT(16)` и `DECFLOAT(34)`](https://www.ibm.com/docs/en/SSEPGG_11.5.0/com.ibm.db2.luw.sql.ref.doc/doc/r0008469.html). Формально IBM называет это «an IEEE 754r number with a decimal point» и параметры не именует, но совпадение однозначное: 16 цифр с экспонентой −383…384 — это decimal64, 34 цифры с −6143…6144 — это decimal128.

Он же единственный, у кого под это есть железо, — но здесь надо аккуратно с моделями. Аппаратный блок десятичной плавающей точки впервые появился в **IBM POWER6** (2007). У мейнфреймов System z9 сама возможность DFP была реализована «with a mixture of low-level software and hardware assists», а настоящий аппаратный блок — только в **z10**, и он выведен из POWER6-шного. Первоисточник — статья [Schwarz, Kapernick, Cowlishaw «Decimal floating-point support on the IBM System z10 processor»](https://www.research.ibm.com/publications/decimal-floatingpoint-support-on-the-ibm-system-z10-processor), IBM Journal of Research and Development, январь 2009. Каноническая справка по всей этой арифметике — [сайт Майка Каулишо про General Decimal Arithmetic](https://speleotrove.com/decimal/), оттуда же растёт библиотека decNumber.

А самое полезное для нас — у двух самых свежих систем в списке. **DuckDB** в [документации по числовым типам](https://duckdb.org/docs/current/sql/data_types/numeric) предупреждает прямым текстом:

> Performance can be impacted by using too large decimals when not required. In particular, decimal values with a width above 19 are slow, as arithmetic involving the INT128 type is much more expensive than operations involving the INT32 or INT64 types. It is therefore recommended to stick with a WIDTH of 18 or below, unless there is a good reason for why this is insufficient.

**ClickHouse** в [документации по Decimal](https://clickhouse.com/docs/sql-reference/data-types/decimal) говорит то же самое почти теми же словами:

> Because modern CPUs do not support 128-bit and 256-bit integers natively, operations on Decimal128 and Decimal256 are emulated. Thus, Decimal128 and Decimal256 work significantly slower than Decimal32/Decimal64.

Из этого следует вывод, который стоит держать в голове всякому, кто мечтает переписать numeric на «быстрое 128-битное целое». Два независимых движка, оба построенные вокруг скорости, оба документируют одно и то же: **128 бит — это уже не регистровая арифметика.** Что подтверждается и ассемблером из шестой причины.

И вот тут неприятная арифметика для любого «быстрого numeric». Чтобы уместить 34–38 значащих цифр, нужны 128 бит — то есть медленная ступенька. Чтобы попасть в быструю, нужно ограничиться 18 цифрами и 64 битами. Ровно поэтому DuckDB и ClickHouse дают пользователю выбирать ширину явно, а PostgreSQL с его единым типом на все случаи такого выбора предложить не может.

## Отступление: а decimal128 не спасёт?

Обычно в этом месте говорят: «зато для денег numeric — единственный правильный выбор, float тут не годится». Формулировка распространённая, но верна она только про *двоичный* float, а это не весь float. Давайте разберём аккуратно.

Почему двоичный float для денег не годится, показать легко:

```sql
select 0.1::float8 + 0.2::float8 = 0.3::float8;   -- false
select (0.1::float8 + 0.2::float8)::text;         -- 0.30000000000000004
```

Десятичная дробь `0.1` не имеет конечной записи в двоичной системе — ровно так же, как `1/3` не имеет конечной записи в десятичной.

Но в базе данных есть аргумент посильнее, специфичный именно для СУБД. Сложение чисел с плавающей точкой не ассоциативно:

```sql
select (1e16::float8 + 1.0 - 1e16::float8)::text;   -- 0
select (1e16::float8 - 1e16::float8 + 1.0)::text;   -- 1
```

Три одинаковых числа, разный порядок сложения — разный ответ. А порядок суммирования в базе вы не контролируете: планировщик волен выбрать другой план, включить параллельную агрегацию и сложить частичные суммы в том порядке, в каком воркеры закончат работу. То есть один и тот же запрос по одним и тем же данным может дать разные итоги в разных прогонах. Для отчётности это дисквалифицирующее свойство, и документация PostgreSQL говорит об этом прямо — правда, не в разделе про numeric, а в [8.1.3 «Floating-Point Types»](https://www.postgresql.org/docs/current/datatype-numeric.html): «If you require exact storage and calculations (such as for monetary amounts), use the numeric type instead».

Всё это — про двоичный формат. А теперь то, о чём в таких разговорах обычно забывают.

**IEEE 754, начиная с редакции 2008 года, определяет и десятичные форматы:** decimal32, decimal64 и decimal128. Это настоящая плавающая точка — со знаком, мантиссой, экспонентой и всеми режимами округления, — но основание системы счисления десять. Значит `0.1` представима точно, и первый аргумент против float на них попросту не действует. decimal128 — это 34 значащих десятичных цифры, экспонента (в терминах стандарта, emin…emax) от −6143 до +6144 и ровно шестнадцать байт.

И тут самая красивая деталь во всей истории. В IEEE 754 у десятичных форматов есть **когорты**: одно и то же число имеет много представлений. Стандарт определяет для каждой операции «предпочтительную экспоненту» результата (для сложения `min(Q(x), Q(y))`, для умножения `Q(x)+Q(y)`, для деления `Q(x)−Q(y)`), а отдельная операция `quantize` приводит число к нужной экспоненте.

У нуля представлений ровно 12288, и арифметика тут занятная: показатель степени хранится смещённым, bias = 6176, диапазон квантовых экспонент от −6176 до +6111 — это 12288 значений; они же складываются из кодировки как 3 × 2¹² (две старших цифры экспоненты из комбинационного поля плюс 12-битное поле продолжения). Мантисса нуля одна, отсюда и 12288 битовых картинок одного и того же нуля.

Узнаёте? Это ровно тот `dscale`, о котором была четвёртая причина. Комитет IEEE проектировал десятичную арифметику с чистого листа, ни на какой PostgreSQL не оглядываясь, — и пришёл к той же самой конструкции. Потому что она не прихоть реализации: если вам нужна точная десятичная арифметика, в которой `1.50` печатается как `1.50`, у одного значения неизбежно будет много представлений, и все сравнения придётся делать с оглядкой на это.

Так почему в PostgreSQL нет decimal128?

Попытки были, и обе поучительны.

[Ветка Крейга Рингера 2013 года](https://www.postgresql.org/message-id/flat/51B7B932.3000407%402ndquadrant.com) предлагала добавить DECIMAL32/64/128 поверх gcc-шных `_Decimal*` с неявным приведением к numeric. Тред закрылся в тот же день ответом Тома Лейна: аппаратной поддержки на массовом железе нет, а «the effort would be a lot more usefully spent on trying to make the existing NUMERIC support go faster». Патча так и не написали.

[Ветка Фэна Тяня 2015 года](https://www.postgresql.org/message-id/CAFWGqnsuyOKdOwsNLVtDU1LLjS=66xmxxxS8Chnng_zSB5_uCg@mail.gmail.com) — уже с работающим расширением [pgdecimal2](https://pgxn.org/dist/pgdecimal2/) поверх библиотеки decNumber, развитие более раннего pgDecimal Павла Стехуле. Здесь надо поправить цифру, которая часто цитируется. Автор написал в письме: «Compared to numeric type, decimal64 arithmetics is about 2x faster, decimal128 is about 1.5x faster» — и это единственное место, где такие числа встречаются. В [README самого проекта](https://github.com/vitesse-ftian/pgdecimal) опубликованы конкретные тайминги, и они скромнее: полиномиальный запрос по 1 млн строк — numeric(15,3) 1763,8 мс, decimal64 1090,8 мс (1,62×), decimal128 1387,0 мс (1,27×); сортировка — 1,23× и 1,11×; hash join — 1,33×. Замерено на Core i5 5252U 1,6 ГГц, против **ограниченного** `numeric(15,3)`, и — что важно — на сборке Vitesse DB с отключённым через `set vitesse.enable = 0` JIT, а не на ванильном PostgreSQL; версия PostgreSQL нигде не названа. Дэвид Роули спросил в треде про железо и не получил внятного ответа; независимо цифры никто не воспроизводил.

Заменой numeric это не стало по нескольким причинам:

- **34 цифры против практически неограниченных.** numeric в PostgreSQL держит [«up to 131072 digits before the decimal point; up to 16383 digits after the decimal point»](https://www.postgresql.org/docs/current/datatype-numeric.html) (объявить в `NUMERIC(p,s)` при этом можно точность не выше 1000). Для денег 34 цифры за глаза, но numeric — тип общего назначения, и обрезать его домен ради скорости никто не станет. Ровно та же логика, что у Лейна в 2001-м: «I do object to emasculating the type we have».
- **Аппаратной поддержки на x86 нет и не было.** Инструкции десятичной плавающей точки есть у IBM POWER начиная с POWER6, у мейнфреймов z начиная с z10, а также у Fujitsu SPARC64 X/X+. На x86 ни один вендор такого не выпускал: то, что предлагает Intel, — это [программная библиотека](https://www.intel.com/content/www/us/en/developer/articles/tool/intel-decimal-floating-point-math-library.html) в кодировке BID. (BCD-инструкции x87 `FBLD`/`FBSTP` — это конвертация целых, не IEEE-арифметика, путать не надо.)
- **Лицензия.** Прозаично, но именно на этом встало расширение: decNumber, по словам самого автора в треде, «is either GPL, or ICU license».
- **Семантика SQL другая.** `NUMERIC(15,2)` в стандарте — точный тип с *объявленным* масштабом, и масштаб результата определяется правилами для сложения и умножения. В decimal128 экспонента результата есть следствие операции, а не контракт колонки. Реализуя `NUMERIC(p,s)` поверх decimal128, весь учёт масштабов придётся вести сверху — то есть делать ровно ту работу, которая numeric и удорожает.

И вывод, ради которого этот раздел вообще в статье. Замеры Фэна Тяня — про арифметику. А мы с вами весь текст выясняли, что в группировке по двадцати колонкам арифметики нет вовсе: там разбор кортежа, копии на каждом вызове и сравнение. Так что главный выигрыш decimal128 в PostgreSQL был бы вовсе не в том, что он десятичный, а в том, что он **фиксированной ширины**: шестнадцать байт, никакой varlena, никакого укороченного заголовка, никаких копий на каждом сравнении и работающий кэш смещений при разборе кортежа.

Это, кстати, ровно то, на чём в 2017 году застрял Томас Манро, [заметив](https://www.postgresql.org/message-id/CAEepm%3D1-roLc59TdBQPvZQQBbNs-sFRjri-HySQ2B8GSuTD7oQ%40mail.gmail.com), что DECFLOAT попал в стандарт SQL (фича T076): decimal32 и decimal64 можно было бы передавать по значению, decimal128 — нет, а механизма «один тип, две дисциплины передачи» в PostgreSQL нет.

Иначе говоря, decimal128 интересен ровно тем же, чем оказалась интересна вторая половина этой статьи. Только с готовым стандартом вместо самодельного формата.

## Так в чём же ниша numeric?

Раз уж мы дошли до сюда, стоит ответить на вопрос, который напрашивается: если numeric
такой дорогой, а весь остальной мир обходится 38 цифрами, зачем PostgreSQL держит 131072?

Сначала — что *не* является ответом.

**Астрономия — миф.** В [обзоре Дэвида Бейли по высокоточной арифметике в математической
физике](https://www.mdpi.com/2227-7390/3/2/337) вся высокая точность делается двоичными
библиотеками: double-double (~31 цифра), quad-double (~62), дальше MPFR и GMP. Тип СУБД
там не участвует. Криптография — то же самое: GMP и `bytea`, а не numeric.

**Биржевая торговля — тоже нет.** FIX
[гарантирует «up to fifteen significant digits»](https://fiximate.fixtrading.org/en/FIX.Latest/fix_datatypes.html)
для `Price`, `Qty` и `Amt`, а регулятор ограничивает сверху:
[SEC Rule 612](https://www.sec.gov/divisions/marketreg/subpenny612faq.htm) запрещает
котировать акции дороже доллара с шагом мельче цента, дешевле доллара — мельче одной сотой
цента. Крипто-биржи щедрее ровно вдвое: `price_increment` у Coinbase и `baseAssetPrecision`
у Binance — восемь знаков. Трейдингу numeric нужен не ради диапазона, а ради отсутствия
двоичного округления.

И самим финансам столько не нужно. Каулишо [посчитал по обследованию 51 организации](https://speleotrove.com/decimal/decifaq1.html):
«Data are typically stored with 18 digits of precision with 6 digits after the decimal
point», «typically a precision of 25-30 digits is used». Собственно, и число 34 в
decimal128 выбрано не от потребностей: кодировка DPD требует длины вида 3k+1, а снизу
подпирает ISO COBOL 2002 с его требованием 32-значных промежуточных результатов — 31 не
проходит, следующий кандидат 34.

А теперь то, что ответом является.

**Первое: EVM-блокчейны.** `uint256` требует **78 значащих цифр** — вдвое больше, чем даёт
`decimal(38)`, и на одну больше, чем `BIGNUMERIC` в BigQuery. И это не экзотика: The Graph
[отображает `BigInt` прямо в `numeric`](https://raw.githubusercontent.com/graphprotocol/graph-node/master/store/postgres/src/relational.rs)
(`ColumnType::BigInt => "numeric"`), то есть каждый субграф в мире хранит балансы именно
так; Blockscout заводит [`value numeric(100)`](https://github.com/blockscout/blockscout/blob/master/apps/explorer/priv/repo/migrations/20180117221923_create_transactions.exs).
А те, у кого потолок 38, честно расписываются в поражении: Google Cloud Blockchain
Analytics [отдаёт значение дважды](https://docs.cloud.google.com/blockchain-analytics/docs/uint256) —
«An UINT128 NUMERIC column **with potential loss of precision**» плюс строкой; Dune ушла с
PostgreSQL на Trino и тут же [допилила движок нативными UINT256](https://docs.dune.com/query-engine/datatypes);
у Elasticsearch [issue про это открыт с 2019 года](https://github.com/elastic/elasticsearch/issues/38242).
В промежуточных вычислениях бывает и больше: произведение двух `uint256` — до 156 цифр.

PostgreSQL здесь — единственная мейнстрим-СУБД, которая справляется без единой строчки
кода. Не потому что кто-то предвидел Ethereum в 1998 году, а потому что произвольная
точность оказалась правильным решением. numeric выиграл лотерею, в которую не покупал
билет.

**Второе, и куда более массовое: сама арифметика.** Разрядность вылезает за 38 без всякого
домена.

```sql
-- миллион строк по 38 девяток
select length(sum(x)::text)
from (select repeat('9',38)::numeric as x from generate_series(1,1000000)) t;
-- 44

select scale(1.000000000000000001::numeric
           * 1.000000000000000001
           * 1.000000000000000001);
-- 54
```

В первом случае каждое значение помещается в 38 цифр, а сумма — уже нет: `NumericSumAccum`
расширяется по мере надобности. Во втором три сомножителя, все примерно равные единице,
дают масштаб 54. Никакого «домена, которому нужно 54 знака», тут нет — есть `GROUP BY` по
большой таблице и три умножения. Крайний случай приводит тот же Каулишо: точное `R^365`
для годовой ставки по дневной [требует 2191 цифру](https://speleotrove.com/memowiki/files/cowlis2003-DFP-algorism.pdf).

**Так умирает numeric или нет?** Точный десятичный тип — точно нет: ISO 20022 закончил
период сосуществования с MT [22 ноября 2025](https://www.swift.com/standards/iso-20022/iso-20022-faqs/implementation),
Банк России идёт туда же к 2029-му, C23 внёс `_Decimal32/64/128` в стандарт языка.
Умирает конкретная конструкция — **произвольная точность переменной длины**. Её не копирует
никто: 38 цифр у Snowflake, Redshift, SQL Server, Spark, DuckDB, Iceberg; Arrow фиксирует
ровно четыре ширины и в 2024 году [добавил более узкие](https://arrow.apache.org/blog/2024/10/28/18.0.0-release/),
а не более широкие. Прямее всех высказался CedarDB, наследник Umbra,
[в документации](https://cedardb.com/docs/references/datatypes/numeric/):

> PostgreSQL offers a maximum precision of 131072 and scale of 16383, where CedarDB
> restricts precision and scale to a maximum of 38, **for performance reasons**.

Проблема, стало быть, не в существовании numeric, а в его **монополии**. У DuckDB четыре
ступеньки (INT16/32/64/128), у Redshift две, у CedarDB две, у Arrow четыре. У PostgreSQL
одна — и она рассчитана на 131072 цифры, даже когда в колонке лежит `numeric(15,2)`.

Забавно, что против второй ступеньки никто и не возражал. Том Лейн ещё в 2001-м:
«I don't have any objection in principle to an additional datatype "small numeric"». Роберт
Хаас в 2017-м [сформулировал ровно тот аргумент](https://postgrespro.com/list/thread-id/1876527),
к которому мы пришли в этой статье: «the fact that the datatype could be pass-by-value
rather than a varlena might speed things up quite a bit in some cases». Просто каждый раз
разговор заканчивался словами «пусть кто-нибудь напишет расширение» — расширение писали
трижды ([pgDecimal](https://github.com/okbob/pgDecimal),
[pgdecimal2](https://github.com/vitesse-ftian/pgdecimal),
[fixeddecimal](https://github.com/2ndQuadrant/fixeddecimal)), и все три мертвы. Последнее
обсуждение в hackers — 13 ноября 2018 года.

## Что с этим делать сегодня

Ничего из перечисленного не означает, что numeric надо избегать. Двоичный float в качестве замены не годится по причинам из предыдущего раздела, а десятичного в ядре PostgreSQL пока нет. Но раз мы теперь знаем, где именно numeric дорог, можно не платить там, где не нужно.

**Numeric дорог в ключах, а не в значениях.** Хранить в numeric суммы — нормально. Группировать по numeric, джойнить по numeric, строить по нему индекс и сортировать — вот где начинается цена. Цифра из замера Cybertec выше — +34 % на джойне при одинаковом размере индекса — про это и есть. Если у вас есть выбор, суррогатные ключи и коды делайте целочисленными.

**Считайте, сколько numeric-колонок попадает в `GROUP BY`.** Стоимость растёт линейно от их количества, и на двадцати колонках она уже доминирует над всем остальным. Часто половину из них можно вынести из ключа группировки — например, взять через `min()` или `any_value()`, если они функционально зависят от остальных.

**Следите за тем, чтобы numeric не появился там, где вы его не звали.** Два классических способа наступить на это, не объявив ни одной numeric-колонки:

- `sum(bigint)` и `avg(bigint)` считаются через numeric, потому что сумма bigint может переполниться. Именно это объяснял Хейкки Линнаканген в [BUG #12675](https://www.postgresql.org/message-id/54C778BF.3000205%40vmware.com), где пользователь недоумевал, почему `double precision` быстрее `bigint` больше чем вдвое: «arithmetic on numeric is much slower than on double».
- Целочисленный литерал, не влезающий в bigint, парсится как numeric — и сравнение `bigint_col = <numeric>` приводит **колонку** к numeric, после чего индекс по bigint становится неприменим. Лукас Фиттл [разобрал реальный случай](https://pganalyze.com/blog/5mins-postgres-large-integers-causing-sequential-scan-instead-of-using-index): index scan ~0,1 мс превращается в параллельный seq scan ~100 мс.

**Обращайте внимание на масштаб констант в запросах.** Быстрый путь сравнения срабатывает, когда представления совпадают. Условие `where amount = 100` и условие `where amount = 100.00` для колонки `numeric(15,2)` дадут один результат, но пойдут разными путями внутри.

**Не гонитесь за экономией на предагрегации.** Если вы группируете миллионы строк по numeric-измерениям, любое сокращение числа строк до агрегации окупается лучше обычного — вы экономите не только на самой агрегации, но и на всех этих аллокациях.

**И не переписывайте деньги в bigint-копейки просто так.** Это работает, это быстро, но вы берёте на себя всю арифметику масштабов вручную — со всеми правилами округления, которые numeric реализует за вас и, что важнее, реализует одинаково во всех местах вашей системы. Обменивать корректность денежных расчётов на полтора раза производительности стоит только тогда, когда вы точно упёрлись именно в это.

И последнее, методологическое. Если соберётесь мерить сами — не берите `sum()` в качестве теста. Том Лейн назвал [такой бенчмарк](https://www.postgresql.org/message-id/19101.1180967738%40sss.pgh.pa.us) «100 % faulty» ровно по причине из предыдущего пункта: «we sum ints in a bigint and bigints in a numeric to avoid overflow». Для честного сравнения типов лучше `max()`.
