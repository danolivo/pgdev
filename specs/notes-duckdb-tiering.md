# Как устроены «ступени» decimal в DuckDB и что из этого применимо в PostgreSQL

Заметка к `task_numeric_fixed_width.md`. Всё проверено на DuckDB 1.5.5 и по исходникам
обоих проектов; строки указаны для `duckdb/main` и `postgres/master` на 8 августа 2026.

---

## 1. Что делает DuckDB

### 1.1. Один логический тип, физическое представление выводится из ширины

`src/common/types.cpp`, `LogicalType::GetInternalType()`:

```c
case LogicalTypeId::DECIMAL: {
    auto width = DecimalType::GetWidth(*this);
    if      (width <= Decimal::MAX_WIDTH_INT16)  return PhysicalType::INT16;   /* ≤ 4  */
    else if (width <= Decimal::MAX_WIDTH_INT32)  return PhysicalType::INT32;   /* ≤ 9  */
    else if (width <= Decimal::MAX_WIDTH_INT64)  return PhysicalType::INT64;   /* ≤ 18 */
    else if (width <= Decimal::MAX_WIDTH_INT128) return PhysicalType::INT128;  /* ≤ 38 */
```

Границы заданы шаблоном `DecimalWidth<T>::max` в `types/decimal.hpp`: 4 / 9 / 18 / 38.
`DECIMAL(39,…)` — ошибка связывания («DECIMAL type width must be between 1 and 38»).

Пользователю ступень не видна: `typeof(cast(1 as decimal(18,2)))` → `DECIMAL(18,2)`,
в `duckdb_columns()` тоже только логический тип.

### 1.2. Ступень выбирается на этапе связывания, не в рантайме

Каждая арифметическая операция над decimal биндится через `BindDecimalMultiply` /
`BindDecimalAddSubtract` (`src/function/scalar/operator/arithmetic.cpp`). Bind вычисляет
ширину и масштаб результата, строит `LogicalType::DECIMAL(w,s)` и подбирает физическую
функцию по `result_type.InternalType()`. В цикле исполнения работает мономорфная функция
над `int64` или `int128` — ветвлений по ступени там нет.

### 1.3. И DuckDB сознательно НЕ повышает ступень, если может остаться в дешёвой

`BindDecimalMultiply`, строки 999–1007:

```c
if (result_width > Decimal::MAX_WIDTH_INT64 && max_width <= Decimal::MAX_WIDTH_INT64 &&
    result_scale < Decimal::MAX_WIDTH_INT64) {
    bind_data->check_overflow = true;
    result_width = Decimal::MAX_WIDTH_INT64;
}
if (result_width > Decimal::MAX_WIDTH_DECIMAL) {
    bind_data->check_overflow = true;
    result_width = Decimal::MAX_WIDTH_DECIMAL;
}
```

То есть: если оба операнда влезли в int64, а точная ширина результата — нет, ширину
обрезают обратно до 18 и включают рантайм-проверку переполнения. Замерено:

```
dec(9,2)  * dec(9,2)   →  DECIMAL(18,4)
dec(18,2) * dec(18,2)  →  DECIMAL(18,4)   ← а не 36,4, хотя 36 < 38
dec(19,2) * dec(19,2)  →  DECIMAL(38,4)   ← max_width 19 > 18, правило не сработало
dec(4,2)  + dec(4,2)   →  DECIMAL(5,2)
dec(18,2) + dec(18,2)  →  DECIMAL(18,2)
```

Плата за это — падение на конкретных данных:

```sql
select cast(100000000000000000 as decimal(18,0)) * cast(10 as decimal(18,0));
-- Out of Range Error: Overflow in multiplication of DECIMAL(18) (100000000000000000 * 10)
```

Тот же расчёт в `decimal(38,0)` проходит.

### 1.4. Чем ещё DuckDB заплатил за фиксированную ширину

**Деления нет.** `typeof(dec(18,2) / dec(18,2))` → `DOUBLE`; `1/3` даёт
`0.3333333333333333`. Задачу выбора масштаба результата (в PostgreSQL — `select_div_scale`)
DuckDB не решил, а отменил: точного десятичного деления в нём не существует.

**Аккумулятор суммы делает ровно одно повышение:**

```
typeof(sum(dec(18,0)))  →  DECIMAL(38,0)
typeof(sum(dec(38,0)))  →  DECIMAL(38,0)
select sum(x) from s;   -- 1000 строк по 38 девяток
-- Out of Range Error: Overflow in HUGEINT addition
```

**Масштаб при умножении складывается и упирается:** десять множителей со scale 4 дают
«Needed scale 40 to accurately represent the multiplication result, but this is out of
range».

## 2. Что из этого в PostgreSQL не применимо

Чтобы не тратить время на разбор, четыре пункта закрываются сразу.

**Одна ступень внутри одного типа — нет.** `typlen` лежит в `pg_type`, то есть это
свойство типа, а не колонки. Один тип не может быть восьмибайтовым для `numeric(15,2)` и
шестнадцатибайтовым для `numeric(30,2)`. Это тот же блокер, из-за которого numeric вообще
переменной длины (см. §«А как у соседей?» в статье), и обойти его без переделки системы
типов нельзя.

**Обрезание ширины результата с проверкой переполнения — нет.** DuckDB может позволить
себе, чтобы `dec(18,2)*dec(18,2)` падало на некоторых данных. PostgreSQL не может: сейчас
такой запрос работает, и его поломка — регресс. Торговать корректностью за скорость
семантика numeric не даёт.

**Деление в double — нет**, по очевидным причинам.

**И честно про ожидания: главный выигрыш DuckDB от узкой ступени — векторизация.** Узкий
фиксированный тип позволяет гнать SIMD по массиву `int64`. У PostgreSQL построчный
исполнитель; тот же приём даст в разы меньше. Это надо закладывать в прогноз, а не
переносить чужие цифры.

## 3. Что применимо — по возрастанию сложности

### 3.1. Прецедент выбора типа по объявленной точности в PostgreSQL уже есть: `FLOAT(p)`

`src/backend/parser/gram.y`, правило `opt_float`:

```c
else if ($2 <= 24)
    $$ = SystemTypeName("float4");
else if ($2 <= 53)
    $$ = SystemTypeName("float8");
```

Пользователь пишет один синтаксис, парсер выбирает физический тип по объявленной точности.
Ровно та же схема годится для `DECIMAL(p,s)`: `p ≤ 18` → узкий тип, `p ≤ 38` → широкий,
иначе `numeric`. Это и предлагал Крейг Рингер в 2013 году, с той же аналогией.

Блокеры реальные и их надо назвать: `DECIMAL` сейчас алиас `NUMERIC`, и менять его —
слом совместимости; плюс придётся строить полную сеть приведений и операторов между
новыми типами и numeric, а на неявных приведениях в этой области уже обжигались (Питер
Гейган и Джим Нэсби в треде 2015 года предупреждали именно про циклы
`numeric → decimal → numeric`).

### 3.2. Самое дешёвое и никем не занятое: специализация агрегата по typmod

Тут у PostgreSQL уже есть весь механизм, и он практически не используется.

`SupportRequestSimplifyAggref` (`src/include/nodes/supportnodes.h`) позволяет
support-функции агрегата переписать `Aggref` на этапе планирования. Вызывается из
`simplify_aggref()` в `src/backend/optimizer/util/clauses.c`. Потребитель на сегодня
**ровно один** — `src/backend/utils/adt/int8.c`, где `COUNT(ANY)` превращается в
`COUNT(*)`. Механика оттуда:

```c
if (agg->aggfnoid == F_COUNT_ANY && list_length(agg->args) == 1)
{
    TargetEntry *tle = (TargetEntry *) linitial(agg->args);
    Expr       *arg = tle->expr;
    ...
    newagg = makeNode(Aggref);
    memcpy(newagg, agg, sizeof(Aggref));
    newagg->aggfnoid = F_COUNT_;
    PG_RETURN_POINTER(newagg);
}
```

То есть: посмотреть на аргумент, принять решение, вернуть новый `Aggref` с другим
`aggfnoid`. А typmod аргумента здесь доступен — `exprTypmod()` по выражению из
`TargetEntry`; для `sum(amount)`, где `amount` объявлен `numeric(15,2)`, планировщик видит
и точность, и масштаб.

**Предложение:** `sum(numeric)` и `avg(numeric)` при известном typmod с `p ≤ 18`
переписывать на вариант с int128-аккумулятором фиксированного масштаба, приводя результат
к numeric только в финальной функции.

Почему это выглядит выигрышным:

- это ровно тот приём, который Андреас Карлссон применил в 2015 году к `sum(int8)` и
  получил 2,47×, а к `var_samp(int4)` — 3,69× (коммиты `8122e1437e`, `959277a4f5`,
  PostgreSQL 9.5). Для numeric-агрегатов его никто не делал, хотя именно они и есть
  массовая нагрузка;
- семантика не меняется: слагаемых с 18 значащими цифрами нужно порядка 10²⁰, чтобы
  переполнить int128, а на всякий случай можно оставить проверку с откатом на общий путь;
- в отличие от DuckDB, здесь нет никакого «ужать и рискнуть» — просто более узкое
  промежуточное состояние при том же результате;
- на непроквалифицированном `numeric` (typmod = −1) всё работает как раньше, то есть
  риск нулевой.

Ограничение, которое надо проверить: typmod виден только когда аргумент — `Var` или
`Const`; для выражений вроде `sum(a*b)` `exprTypmod` вернёт −1, и специализация не
сработает. Для профиля 1С (`sum(Ресурс)` по колонке) это не помеха.

### 3.3. Bind-time специализация сравнения — идея красивая, но для `GROUP BY` мёртвая

Соблазн такой: `SupportRequestSimplify` применяется не только к `FuncExpr`, но и к
операторам — `simplify_function(expr->opfuncid, ...)` вызывается из `case T_OpExpr` в
`eval_const_expressions_mutator` (`clauses.c:2919`). Если оба операнда `numeric_eq` —
`Var`'ы с одинаковым typmod `numeric(p,s)`, то dscale у них совпадает *по построению*, и
быстрый memcmp-путь корректен без всякой проверки в рантайме. Решение принимается один раз
в планировщике.

**Для сравнения ключей в `HashAggregate` это не работает.** Проверено:
`ExecBuildGroupingEqual()` (`src/backend/executor/execExpr.c:4461`) принимает массив OID'ов
функций равенства прямо из опкласса и строит `FmgrInfo` вручную:

```c
fmgr_info(foid, finfo);
fmgr_info_set_expr(NULL, finfo);
...
scratch.opcode = EEOP_NOT_DISTINCT;
scratch.d.func.fn_addr = finfo->fn_addr;
```

Никакого `OpExpr` в этом пути нет вовсе, поэтому prosupport до него не дотягивается.
Хуже того, `fmgr_info_set_expr(NULL, …)` означает, что `flinfo->fn_expr` равен NULL —
то есть функция сравнения не может даже в рантайме заглянуть в типы своих аргументов.
Опкласс же выбирается по типу, а не по typmod, так что и подменить функцию равенства для
`numeric(15,2)` нельзя.

Это неприятно, но выводы отсюда конструктивные:

- **Никакая plan-time специализация в горячем пути группировки невозможна в принципе.**
  Единственный рычаг — внутри самой `numeric_eq`. То есть подход текущего патча (быстрый
  путь по совпадению байтов, проверяемый в рантайме) не «временное решение вместо
  красивого», а единственно доступное.
- Остаётся применимым там, где `OpExpr` реально есть: обычные квалы (`where amount = 100`),
  выражения в целевом списке. Это не главная нагрузка, и городить ради этого prosupport,
  скорее всего, не стоит.
- И это ещё один довод в пользу §3.2: агрегаты — единственное место, где планировщик
  вообще может что-то специализировать, потому что `Aggref` доживает до
  `eval_const_expressions`, а сравнение ключей — нет.

### 3.4. Узкая ступень в PostgreSQL уже существует — но только в одном месте

Стоит помнить, что приём не нов для дерева. `numeric_abbrev_convert()` в `numeric.c`
(коммит `abd94bcac4`, Эндрю Гирт, PostgreSQL 9.5) уже приводит numeric к int64 и работает
дальше с ним — и там же уже применён трюк с переиспользуемым буфером под packed-датумы:

> This is to handle packed datums without needing a palloc/pfree cycle; we keep and reuse
> a buffer large enough to handle any short datum.

То есть в PostgreSQL уже есть и «узкое представление для быстрого пути», и «не платить за
packed-заголовок» — но только в sortsupport. Расширение этой пары приёмов на хэш и
сравнение и есть предмет патча.

## 4. Сводка

| Приём DuckDB | Применим? | Как именно |
|---|---|---|
| Одна ступень внутри одного типа | **Нет** | `typlen` — свойство типа, а не колонки |
| Обрезать ширину результата + проверять переполнение | **Нет** | сломает работающие запросы |
| Деление в double | **Нет** | — |
| Выбор физического типа по объявленной точности | **Да**, прецедент есть | `FLOAT(p)` в `gram.y`; но `DECIMAL` — алиас `NUMERIC`, нужна сеть приведений |
| Bind-time выбор реализации для агрегата | **Да**, механизм есть и свободен | `SupportRequestSimplifyAggref`, сейчас единственный потребитель — `COUNT(1)→COUNT(*)` |
| Bind-time специализация сравнения ключей | **Нет** | в `ExecBuildGroupingEqual` нет `OpExpr`, а `fn_expr` = NULL |
| Узкий аккумулятор агрегата | **Да, и это самое дешёвое** | int128-аккумулятор при typmod `p ≤ 18`, по образцу `8122e1437e` |
| Векторизация как источник выигрыша | **Ограниченно** | построчный исполнитель; чужие цифры не переносятся |

Порядок, в котором это стоит трогать, по отношению «выигрыш / риск»:

1. **int128-аккумулятор для `sum`/`avg` по typmod** — механизм готов и свободен, семантика
   не меняется, прецедент с числами есть, конкурентов в hackers нет.
2. **Патч по packed-заголовку** (текущий). Проверка §3.3 показала, что альтернативы у него
   нет: в горячем пути группировки выражения отсутствуют как класс, поэтому оптимизировать
   можно только изнутри `numeric_eq`/`hash_numeric`. Это стоит написать прямо в письме в
   hackers — как обоснование, почему решение принимается в рантайме, а не в планировщике.
3. **Отдельный узкий тип с выбором по `DECIMAL(p,s)`** — самое дорогое и самое спорное;
   трижды предлагалось и трижды не прошло, а три написанных расширения умерли.

## 5. Что осталось непроверенным

- Реальный выигрыш int128-аккумулятора для `sum(numeric(15,2))` не измерялся — оценка по
  аналогии с `sum(int8)` (2,47×), а там менялся *весь* тип аккумулятора, тогда как здесь
  входные значения всё равно остаются varlena. Ожидание надо строить осторожно.
- Не проверено, доживает ли typmod до `simplify_aggref` в реальных планах 1С (там запросы
  генерируются с временными таблицами и приведениями, typmod может теряться). Это
  единственное, что осталось между §3.2 и прототипом.
- Не проверено, как поведёт себя int128-аккумулятор при отрицательном масштабе
  (`numeric(p,-s)`, разрешён с PostgreSQL 15) и при `numeric(p,s)` с `s > 18`.
- Не проверено, что делать с `avg`: делитель известен только в финальной функции, поэтому
  узким может быть только накопление суммы, а деление всё равно уйдёт в общий путь.
