# numeric как тип фиксированной длины (сборка 1С-дистрибутива)

Статус: постановка задачи; перед реализацией — решающие замеры (§6).
Цель: **только** vendor-дистрибутив для 1С-класса развёртываний.
В сообщество непереносимо по построению (меняет формат типа).

---

## 1. Идея

Развёртывание гарантирует: ни одного numeric шире 32 значащих цифр
(контракт платформы 1С; 38 цифр — потолок промежуточных вычислений).
Тогда переменная длина numeric — чистый налог: тип можно объявить
**фиксированной длины**, например 24 байта:

```c
typedef struct FixedNumeric
{
	int128		coeff;			/* значение = coeff * 10^(-dscale) */
	int16		dscale;			/* отображаемый масштаб */
	uint16		flags;			/* NaN; ±Inf — по решению §5.4 */
	/* 4 байта паддинга до 24 при typalign 'd' */
} FixedNumeric;
```

`pg_type`: `typlen = 24`, `typalign = 'd'`, `typstorage = 'p'`
(не-TOASTable — при 24 байтах TOAST не нужен).

Что дешевеет радикально и повсеместно, без per-query оговорок:

- **нет varlena-механики вовсе**: ни detoast, ни packed-заголовков, ни
  разбора формата — значение готово к употреблению по указателю;
- **сравнение и хэш — целочисленные**: выровнять масштаб, сравнить два
  int128 — сортировки, btree-поиск, hash join/agg по numeric-ключам
  (с оговоркой §3.5 о бит-точности хэша);
- **арифметика в регистрах** для всех операторов (add/sub/mul точно,
  div/транcцендентные — см. §5.2);
- **фиксированный размер** упрощает deform, оценки ширины строк,
  и делает агрегатные состояния тривиально плоскими. Deform —
  единственная статья расхода, которую не забирает ни один из более
  дешёвых предшественников (§7); это главный аргумент за смену формата.

## 2. Что НЕ меняется

- Текстовый ввод/вывод, синтаксис, typmod-семантика, имена функций.
- **Wire binary**: `numeric_send`/`recv` конвертируют в классический
  base-10000-формат — драйверы и клиент 1С не замечают подмены.
- `pg_dump`/`pg_restore`: нигде не использует binary COPY, только
  текстовый, поэтому dump/restore работает **в обе стороны**, включая
  custom → сток. Это единственное, что делает vendor lock-in обратимым;
  вынесено в критерий готовности §9.4.
- `COPY ... WITH (FORMAT binary)`: едет через send/recv — совместим.
- Логическая репликация через `pgoutput` (текст или `binary = true`) —
  совместима со стоковыми узлами в обе стороны.

Не входит в этот список и требует отдельного решения либо проверки:
бит-точность хэша (§3.5) и протоколы сторонних плагинов логической
репликации (§3.7).

## 3. Цена — инвентаризация без прикрас

1. **Формат на диске меняется.** `pg_upgrade` со стоковой сборки
   невозможен; физическая репликация и basebackup несовместимы со стоком;
   миграция — только dump/restore. Индексы по numeric-колонкам —
   пересоздаются в новом формате автоматически при restore.
2. **Хранение растёт.** `numeric(15,2)` на диске сегодня ~7–11 байт
   (packed varlena; на 1С-профиле значений замерено 7 байт);
   фиксированные 24 байта — рост до ×3 на таких колонках → больше
   страниц → хуже bandwidth сканов. Это способно съесть заметную часть
   арифметического выигрыша на скан-тяжёлых запросах — решающий замер
   §6.1.
3. **Значение шире 32 цифр = ошибка** (`ERRCODE_NUMERIC_VALUE_OUT_OF_RANGE`,
   с текстом, называющим лимит сборки). Контракт платформы делает это
   недостижимым для приложения; достижимо руками администратора — и это
   осознанное поведение сборки, документируемое.
4. **ABI**: любой код, заглядывающий внутрь numeric (расширения,
   самописный C) — пересобрать/адаптировать.

### 3.5. Хэш: несовместимость, которую нельзя допустить молча

`hash_numeric` (`src/backend/utils/adt/numeric.c:2720`) хеширует **массив
base-10000 digits плюс weight**, а не значение как таковое. Обещанный в §1
«целочисленный хэш» по int128 даст другое значение хэша для того же числа.
Последствия, по убыванию тяжести:

- **внешнее хеш-шардирование** (Citus-подобное, самописное на
  `hash_numeric`/`hashtextextended`): констрейнта, который поймает ошибку,
  нет — тихая неверная маршрутизация и молча неполные ответы;
- **hash-партиционирование по numeric-ключу**: `pg_dump` по умолчанию
  грузит данные прямо в листовые партиции, а прямой COPY в партицию
  проверяет partition constraint → restore падает с «violates partition
  constraint» в непонятном месте. Обходится `--load-via-partition-root`,
  но об этом надо знать заранее (§9.4). Логрепликация лист-в-лист между
  стоком и custom-узлом — то же падение apply;
- **GIN `jsonb_path_ops`** (`jsonb_util.c:1459`) и hash-индексы хранят
  хэши на диске; здесь спасает то, что миграция всё равно через restore.

**Решение к фиксации (§5.6): хэш обязан остаться бит-точным.** Это
достижимо без аллокаций — развернуть int128 в digits в стековом буфере и
хешировать как сегодня. Потеря меньше, чем кажется: detoast и разбор
varlena-заголовка исчезают в любом случае, а на packed-датумах это и есть
основная статья (§7).

### 3.6. Амплификация WAL и бэкапа

§3.2 считает страницы и seqscan-bandwidth, но рост кортежа — это ещё и:
объём WAL в сутки, bandwidth физической и логической репликации, размер
PITR-архива, время basebackup и restore, окно RPO. Частично отыграется
сжатием (4 байта паддинга и старшие нули int128 жмутся отлично,
`wal_compression` для FPI), но shared_buffers и bandwidth сканов не
сжимаются. Внесено в замер §6.1.

### 3.7. Границы парка

«Все сервера одинаковые» верно на бумаге и ложно в эксплуатации:
DR-площадка, QA-контейнер с `docker.io/postgres`, хост тестового
восстановления бэкапов, ноутбук разработчика. Тихое смешение = порча
данных, поэтому задача — сделать смешение технически невозможным, а не
маловероятным.

Механизм в ядре уже есть: при старте сервер сверяет catversion и падает с
FATAL «database files are incompatible with server»
(`src/backend/access/transam/xlog.c:4485`). Отсюда **обязательные** пункты
сборки: bump `CATALOG_VERSION_NO` (лучше и `PG_CONTROL_VERSION`) плюс
различимый суффикс в `PG_VERSION_STR`. Тогда сток-бинарь не поднимется на
вашем datadir, а ваш — на стоковом; физрепликация и `pg_rewind` между
линиями отвалятся громко.

Чего это не закрывает:

- **`pg_upgrade` стоковыми бинарями с вашего кластера**: он копирует файлы
  данных как есть, сверяет maxAlign/blcksz/float8-passing, но не typlen
  numeric — новый сток-кластер получит varlena-мусор молча. В вендорный
  `pg_upgrade` добавляется явная проверка в обе стороны (refuse, если у
  старого кластера `numeric.typlen` не совпадает с ожидаемым).
  Использование *стокового* pg_upgrade закрывается только упаковкой и
  политикой — записываем как остаточный риск, честно.
- **Тест-восстановление бэкапов**: pgBackRest `verify` считает чексуммы и
  ему всё равно, а restore + smoke-запрос требует вендорного бинаря на
  верификационном хосте. Правка pipeline, не патч.
- **Внешние парсеры файлов**: `pg_filedump`, `pg_dirtyread`, самописные
  утилиты аварийного извлечения — адаптировать. `pg_waldump`, pgBackRest,
  WAL-G, barman кортежи не разбирают — им всё равно.
- **Сторонние плагины логической репликации.** У pglogical был режим
  передачи *внутреннего* представления базовых типов с рукопожатием по
  `sizeof(Datum)`, выравниванию, `float8byval` и major version. Два узла с
  одинаковым major, но разными форматами numeric такое рукопожатие
  пройдут и передадут внутренний datum → тихая порча. Для Spock проверить,
  что numeric не идёт во внутреннем виде либо что в рукопожатии есть
  различающий идентификатор; сборка своя — достаточно сдвинуть версию
  протокола. Утверждение §2 о совместимости логрепликации доказано только
  для `pgoutput`.

### 3.8. Расширения, хранящие numeric в своём формате

§3.4 говорит «пересобрать», но опасны не те, что читают numeric, а те, что
*пишут* его в собственное хранилище: компрессированные колоночные движки
timescale-типа, columnstore, любые blob-сериализации датумов. Их данные не
переживут смену формата и не чинятся пересборкой. Нужна поимённая
инвентаризация расширений парка до старта. `pg_statistic_ext_data` с
сериализованными MCV в ту же категорию, но пересчитывается ANALYZE.

## 4. Ключевое архитектурное решение: digit-библиотека остаётся внутри

`NumericVar` и вся поразрядная машинерия **не удаляются** — они перестают
быть форматом хранения и становятся внутренней вычислительной
библиотекой: транcцендентные (`ln`, `exp`, `power`, `sqrt`), деление с
его правилами округления, печать — работают конверсией
FixedNumeric → NumericVar → вычисление → обратно. Это сводит объём v1 к
формату + горячим операторам, а не к переписыванию всей математики, и
гарантирует бит-точность там, где digit-код остаётся эталоном.

Побочно это же даёт бит-точный хэш (§3.5): развёртка int128 в digits уже
есть, её достаточно делать в стековом буфере.

## 5. Открытые решения (зафиксировать до кода)

1. **Точный размер/выравнивание**: 24@8 (быстрее) против 20@4 или
   упакованных 17 (компактнее, медленнее доступ) — микробенч.
2. **Деление и округление**: v1 — через digit-библиотеку (§4);
   int128-деление с доказанным паритетом `select_div_scale` — отдельная
   стадия, разделяемая с задачей expression-fastpath.
3. **mul с результатом > 38 цифр**: точное произведение двух 32-значных —
   до 64 цифр; ошибка (контракт: 38 — потолок промежуточных) или
   округление до 38 по правилам стока? Требует сверки с семантикой 1С.
4. **±Inf**: под валидным typmod невозможны; неограниченный numeric в
   этой сборке всё равно ограничен 32 цифрами — предлагается честно
   поддержать NaN и ±Inf флагами (3 бита flags), чтобы домен типа не
   сузился против стока.
5. **Отрицательные/большие typmod-масштабы** (PG15+): поддержать в
   пределах представимости коэффициента, иначе ошибка при вводе.
6. **Бит-точность хэша** (§3.5): предлагается «да, обязательна». Цена —
   развёртка int128 в digits на стеке в `hash_numeric`. Альтернатива
   («быстрый int128-хэш, несовместимость документируется») требует
   явного согласия на то, что hash-партиционирование и внешнее
   шардирование по numeric в парке отсутствуют и не появятся.
7. **Стабильность формата между вендорными мажорами.** Как только формат
   поедет второй раз, теряется `pg_upgrade` внутри собственной линии — а
   это штатный путь обновления парка. Выбранный в §5.1 размер фиксируется
   как долгосрочный контракт.

## 6. Решающие замеры до старта реализации

1. **Хранение, сканы и WAL на реальном 1С-датасете**: перегнать образ базы
   в 24-байтовый формат (достаточно арифметической модели по гистограмме
   ширин колонок) и оценить: рост объёма таблиц/индексов, деградацию
   seqscan-bandwidth, **прирост WAL в сутки и размера суточного бэкапа**
   (§3.6). Если рост объёма > ~30 % на горячих таблицах — вернуться к
   варианту упакованного размера (§5.1) или пересмотреть ROI.
2. **Доля выигрыша, уже забираемая более дешёвыми работами.** Замерять
   нужно *поверх* базовой линии §7, а не поверх стока: часть того, что
   выглядело «арифметическим резервом», оказалась трафиком аллокатора и
   уже снята патчем support-функций. Fixed-width стартует только если
   после expression-fastpath **и** патча §7 профиль всё ещё показывает
   deform/detoast/cmp как значимые статьи.
3. **Дифференциальный корпус хэша** (§3.5): значения `hash_numeric` и
   `hash_numeric_extended` на всём домене ≤ 32 цифр плюс NaN/±Inf, нули
   разного масштаба, граничные weight — против стоковой сборки, побайтово.

## 7. Базовая линия: что уже забирается без смены формата

Замерено на PG20devel, -O2, 1M строк, 20 колонок `numeric(15,2)` против 20
`int4`, минимум из 5 прогонов:

| сценарий | int | numeric | ratio |
|---|---|---|---|
| seqscan + deform 20 колонок | 72 ms | 119 ms | 1.6× |
| `sum(hash_*(c1))`, 1 колонка | 62 ms | 110 ms | 1.8× |
| GROUP BY 20 колонок → 1M групп | 1031 ms | 1572 ms | 1.5× |
| GROUP BY 20 колонок → 1k групп | 459 ms | 1425 ms | **3.1×** |

Разрыв утраивается ровно тогда, когда группы начинают повторяться, то есть
в любой реальной агрегации по измерениям: на каждый зонд хэш-таблицы
`numeric_eq` вызывается по числу колонок. И `numeric_eq`, и `hash_numeric`,
и весь набор компараторов начинались с `PG_GETARG_NUMERIC` →
`PG_DETOAST_DATUM`; значение в кортеже лежит с однобайтовым varlena-
заголовком, поэтому это **palloc + memcpy на каждое значение на каждый
вызов** — 40 аллокаций на строку в сравнении плюс 20 в хэше.

Снято патчем в support-функциях numeric (ветка
`claude/custom-numeric-backup-sync-y77za5`, коммит `4df353c`):

- распаковка packed-значения в буфер на стеке вместо `DatumGetNumeric`
  (`hash_numeric`, `hash_numeric_extended`, `numeric_cmp/eq/ne/lt/le/gt/ge`,
  `numeric_fast_cmp`); откат на общий путь — только для сжатых, вынесенных
  в TOAST и неправдоподобно длинных значений;
- memcmp-быстрый путь в `numeric_eq`: одинаковое хранимое представление
  всегда означает равные значения, а значения одной колонки делят dscale —
  попадание почти стопроцентное. Для равенства корректно, для порядка нет.

| сценарий | было | стало |
|---|---|---|
| GROUP BY 20 numeric → 1k групп | 1425 ms | **826 ms** (−42 %) |
| `sum(hash_numeric(c1))` | 110 ms | 98 ms (−11 %) |
| GROUP BY 20 numeric → 1M групп | 1572 ms | без изменений |
| GROUP BY 20 int (контроль) | 459 ms | без изменений |

Отставание numeric от int в горячем случае: 3.10× → 1.79×. Хэш-значения
побайтово совпали со стоковой сборкой, core-регрессия зелёная (245/245).

Что это значит для настоящей задачи:

- ROI fixed-width считается от **826 ms, а не от 1425 ms**;
- deform остался нетронутым (119 ms против 72 ms) и не берётся ни этим
  патчем, ни expression-fastpath: numeric — varlena, поэтому `attcacheoff`
  перестаёт работать начиная с первой numeric-колонки. Это и есть
  оставшийся уникальный аргумент за смену формата;
- патч не меняет ни семантики, ни хэш-значений, поэтому переносим в
  сообщество независимо от судьбы этой задачи.

## 8. Взаимодействие с другими работами

- **Патч support-функций numeric** (§7) — предшественник; ставится первым,
  дешёвый, коммьюнити-переносимый, и меняет базу отсчёта для §6.2.
- **Патч агрегатов** (int128 fast path) — совместим; при fixed-width
  быстрый путь агрегатов упрощается (декодер тривиален).
- **Expression-fastpath** — предшественник и поставщик ядра: int128-ядра
  операторов пишутся там и переиспользуются здесь; дифференциальный
  корпус общий.
- **PHA / shared-memory агрегация** — fixed-width делает numeric-состояния
  плоскими «бесплатно», усиливая мотивацию, но не являясь её условием
  (плоский transition-тип достижим и без смены формата).

## 9. Критерии готовности v1

1. Полная регрессия ядра зелёная (кроме тестов, законно упирающихся в
   32-значный лимит — их список зафиксирован и объяснён).
2. Дифференциальный корпус против стока: бит-точность текстового вывода,
   send-образа **и значений `hash_numeric`/`hash_numeric_extended`** для
   всего домена ≤ 32 цифр, NaN/±Inf (§3.5, §5.6).
3. Замеры: сравнение/хэш/сортировка по numeric-ключам, арифметика
   выражений, сканы (рост объёма учтён), WAL/сутки и размер бэкапа
   (§3.6), shagg-корпус — A/B против базовой линии §7.
4. Миграционная инструкция dump/restore:
   - pre-flight по всему парку до миграции: есть ли numeric шире 32
     значащих цифр (иначе restore падает на середине, а логрепликация
     сток → custom встаёт на конкретной строке без простого пропуска);
   - `--load-via-partition-root` для hash-партиционированных таблиц с
     numeric-ключом, если решение §5.6 всё же допустит смену хэша;
   - проверка обратного пути custom → сток (§2) как штатного exit path;
   - проверка логической репликации со стоковым узлом в обе стороны —
     отдельно для `pgoutput` и отдельно для Spock (§3.7).
5. Сборка: `CATALOG_VERSION_NO` и `PG_CONTROL_VERSION` сдвинуты, суффикс в
   `PG_VERSION_STR`, проверка `numeric.typlen` в вендорном `pg_upgrade`
   в обе стороны, остаточный риск стокового `pg_upgrade` задокументирован
   (§3.7).
6. Инвентаризация расширений парка на предмет собственного хранения
   numeric-датумов (§3.8) — с вердиктом по каждому.
